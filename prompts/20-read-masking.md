## Objective

S14b says the web UI masks flagged values by default. `contract/08-web` fixed how (option M1: the registry masks at the REST edge, never in a port) and assigned the work to 05. Prompt 05 did not build it (D128), so today every signed-in Viewer receives flagged values in clear in file text, diffs, search lines, served text and blobs. The settings surfaces (effective config, grid, settings search) are already masked by the index (D95).

Build it in `crates/hub-registry`:

- every REST read response that carries file, diff, search or served text goes out with each flagged value replaced by `[REDACTED: N chars, rule]`, and with the `masks` list where the contract has one (`FileContent`, `ServedFile`);
- unmasked text is unrepresentable at that edge;
- the ETag of a masked response carries the version of the scan;
- `RegistryBlobPolicy` refuses the hash of a text file whose text the scan flags;
- a planted-key test proves it over every GET operation.

The ports stay raw. hub-writes reads raw bytes through `RegistryRead::content` for edits, PRs, previews and reveal, and hub-mcp masks its own copy. `docs/interfaces.md` (CG7) puts masking at the REST edge and never in a port; the tests of T4 to T6 hold the ports raw.

Prompt 05 is merged and owns this crate, so this prompt owns only the paths in the table. The plan lists `docs/decisions.md`, `docs/interfaces.md` and `crates/xtask/tests/budgets_registry.rs` as Extra-paths and requests the `perf/budgets.toml` rows as a contract change (the precedent of 05, 06 and 07: rows with `registered = false` first, flipped in the commit of each harness).

## Defaults the plan confirms

An investigation and three independent reviews of this prompt left these open. The plan answers each, and a human confirms the answers when approving it. Where the plan has no better answer, use the default.

1. **Where masking lives.** In the REST edge of `crates/hub-registry`. The REST handlers hold only `&dyn RegistryApi` (`read/api.rs`, not a port). It gets `scan_version()`, `content_masked(..)`, `served_masked(..)`, `compare_masked(..)` and `search_text_masked(..)`; each returns the masked text, the masks and the tag, and the compare also returns the content hash of each side that has text. The REST handlers call only these. The existing `*_tagged` methods and every `RegistryRead` method stay raw, with their types.
2. **Scan the whole blob, keyed by the exact bytes.** Scan the whole decoded text, then map the matches to lines. Never scan a cut search hit or one hunk: a PEM body line is flagged only by a scan that saw the header, and a token that straddles the 512-byte cut of a hit can fall under the 32-character threshold. The scan result is keyed by (`ports::content_hash` of the exact bytes that were decoded and scanned, scan version): the blob for a file read, the served bytes for a served file, the `Text::Bytes` of a compare side. Never by `Side.hash`, `Resolved.hash`, `Effective::hash` or any stored hash: an effective hash is a hash of merged settings, so two files with equal settings and different comments share it, and a token in a comment would reach a Viewer.
3. **Scan version.** `ScanVersion` is the SHA-256 of the `ScanConfig` fields, the input limit the registry scans with, a registry constant `MASK_FORMAT`, and the matches that `secret_scan` returns over a probe text. The probe is built at run time from parts and never committed as literals (S10, rule 12); it holds one value of each rule, a PEM block, a JWT, each known prefix, and tokens at the minimum length and one below it. A change in what the engine flags therefore changes the version with nobody bumping a constant. The engine has no list of its rules, so the registry also matches on `SecretRule` exhaustively in one function, with no wildcard arm, and a new variant fails to compile. No engine edit. The registry has one source of `ScanSettings` (`ScanConfig` and `Limits`) for its own code, where `read/service.rs`, `index/settings.rs` and `adoption/mod.rs` each call `ScanConfig::default()` today. hub-writes and hub-mcp keep theirs: a retune in the engine reaches all of them through `ScanConfig::default()`, and the registry diverges only if `RegistryConfig` sets a non-default scan.
4. **The settings index and a retune.** The index keeps the verdict of the day it was indexed (D95). A retune that flags more than the index did would leave those values in clear in the effective config, the grid, the settings search and `setting_changes` while the file text masks them. So the retune must include a re-index data job (delete the marker rows of `settings_index_blobs` and their `settings_index` rows, which `lanekeeper_app` may do; the sweeper then indexes the blobs again), and the new scan version is not activated before it has run. This prompt does not build the job; the threat model states it as a go-live condition.
5. **Limits.** Decode a file's bytes under the plain limits and scan the decoded text with `input_bytes` doubled, as write validation does (`text_limits` in `crates/hub-writes/src/pipeline/validate.rs`, used there and in `prs/plan.rs`), so that a 2 MiB Latin-1 or UTF-16 file whose decoded text is longer than `input_bytes` is not withheld on read. Reveal does not do this (`view::side` in `proposals/view.rs` and `preview/effect.rs` scan under the plain limit and treat a failed scan as "every setting is masked"), so for such a file reveal accepts more settings than the masks name. That is the safe direction and an Editor reveals one audited value at a time; record it and do not edit hub-writes.
6. **Fail closed, per surface, and say which failures are cached.** A deterministic failure is `Unscanned(TooLarge | TooManyMatches | NotText)`; `NotText` is a decoded text that holds a NUL byte (UTF-16 without a byte-order mark decodes with NULs between the letters and hides every token) or that does not decode. It is cached with the matches. A transient failure (no scan permit in time, a store error, a join error, a cancelled scan) is never cached: the request fails closed and the next one tries again, because cached transient failures would let a Viewer who saturates the permits poison legitimate files. The surfaces:
   - `getFileContent`, `getServedFile`: deterministic gives `content_withheld: true` and `text: null` (the contract); transient gives 503 `unavailable` with `Retry-After`, the operations' documented `default` response.
   - `compareFile`: deterministic compares the unscannable side by hash only, as an undecodable side is compared today (`binary` carries both hashes and sizes; `hunks` and `setting_changes` are empty); transient gives 503 with no detail (`ReadError::Unavailable`; ports has no other variant).
   - Search: omit the hit and count it in a metric without file or hash label, and never fail the request, because a file that cannot be scanned (more than 100,000 matches, or text that does not decode) can reach the store from NFS, Git or an agent although hub-writes refuses to write one, and one such file must not break every search. This departs from `docs/interfaces.md` (a problem response where the schema has no `content_withheld`); the new decision records it.
   - Blob policy: refuse.
7. **ETag.** The tag of a masked response carries the scan version, and so does the tag of a response withheld because the scan could not finish; a denied file keeps the hash. A 304 is answered before any decode, scan or mask. It is also answered before the blob is read for `nfs`, `baseline` and `blob` content only: a Git read needs its bytes for the hash, a compare loads both sides first, and a served file needs the agent round trip; none of these is restructured.
8. **Lines and offsets.** For `FileContent` and `ServedFile`, `Mask.line` counts line feeds only (the contract), while the scan also ends a line at a lone CR: convert each match to a byte offset in the whole text and derive the line from the number of `\n` before it, so no contract change is needed. Search hits and diff lines use the scan's own lines (the engine ends a search line at `\n`, `\r\n` or a lone `\r`, as the scan does, so `hit.line` equals `SecretMatch.line`). `start` and `end` are UTF-8 byte offsets into the masked text, on character boundaries. N in a marker is the flagged span's length in characters (the engine's `SecretMatch::marker`). `masks` and the range remapping come from the replacement table built while masking, never from a search of the output for the marker pattern: a source text that already contains `[REDACTED: 12 chars, high_entropy]` is returned unchanged, with no mask entry and no effect on the 1,000 cap.
9. **`Mask.setting`.** Set only for a structured file, from a fresh parse and flatten of the decoded text (the way `view::side` does it, not from the settings index), when exactly one setting's line range covers the marker's line and `view::marker` would accept that setting; otherwise absent, which means no reveal. That is stricter than `view::marker` alone, which accepts every setting whose range holds a flagged line. It is computed per request, after the cached scan and only when the scan found a match, and it is not cached in the scan cache, whose key has no path.
10. **Ranges and the search oracle.** `TextHit.ranges` and the `InlineRange` offsets index the masked text: remap them through the replacement table, and a range that overlaps a marker clamps to the marker. For search the REST edge also closes the extraction oracle of open item 1 of `docs/interfaces.md`: it removes every range that overlaps a flagged span of its line, and drops (and counts, without label) a hit that has no range left while its line holds a flagged span. It also drops a hit whose line holds a flagged span when the match cannot be located in the returned text: `ranges` empty, the 64-range cap reached, or a flagged span that starts at or after the 512-byte cut. No port change. Residuals to record: the hit count and `truncated` still depend on dropped hits, and MCP search (which shares the port) keeps the oracle. Compare equality (open item 3) is an equality oracle, not an extraction oracle, and stays. If the human rejects the closure, the threat model must say that a Viewer can extract a flagged value at about six requests per character.
11. **Blob policy.** `RegistryBlobPolicy::new(pool, &config, metrics, scans: Arc<ScanCache>)`, where `ScanCache` is the cache of T3 together with a `BlobStore` handle for misses; `RegistryService` and the policy share one instance (one bound, P11), and a test that needs no service builds its own. The cache holds scan results only; whether a hash is allowed is decided on every request, as today, with the denied checks first and nothing about them cached. The policy reads the blob only after the sightings query ran. A hash is scanned unless every sighting's class is `binary` (a sighting with no class counts as text); when every sighting is binary, the bytes are still scanned if they decode as text with no NUL byte, because text under a binary extension (`.conf`, `.ini`, `.bak`) is common and `getBlob` serves it whole. A binary-class blob larger than `max_file_bytes` is served unscanned, and the threat model records it. A hash with no sighting or no stored blob is allowed as today (the endpoint answers 404 for the second), with no scan and no cache entry. A hash that more than `HASH_PATHS_LIMIT` sightings have had stays refused as undecided, and the rule that a hash is refused if any path that has had it is denied stays. The `BlobPolicy` trait in `hub-platform` is unchanged. Residual: bytes served before this ships stay in browser caches for up to a year (`immutable`).
12. **Cost control.** The scan runs in `spawn_blocking`, and on rayon only when a request scans two or more blobs, on a pool of its own: `scan_threads` (default 1, range 1 to the vCPUs minus one; never the 2-thread read pool that text search uses). At most `scan_concurrency` (default 2) scans run per replica and at most `scan_per_user` (default 2) per `UserId`, in a bounded map. A request that cannot get a permit within `scan_wait` (default 250 ms) fails closed (default 6). The permit moves into the blocking closure and is released when the scan ends, not when the request future is dropped. Decode, scan, mask and serialisation of a request happen while the permit is held, so the memory in flight is `scan_concurrency` times about four times the scan input limit.
13. **Budgets.** The planner has no code and cannot measure a scan that does not exist, so the plan states each new threshold as a rule, in a table whose cells `budgets_registry.rs` quotes, and T3, T5 and T7 measure. A missed rule means `plans/20-read-masking.blockers.md` with the numbers, and a stop; a human sets the threshold, as prompt 04 did. Rules to propose: a scan of a 2 MiB file with one planted private key, p95 at most 25 ms on one thread (`P7.mask_scan`); a planted-secret compare of the 6,000-line file within the 100 ms of `P7.compare_api` (`P7.compare_api_masked`); the blob policy on a miss within the 30 ms of `P7.blob_endpoint` (`P7.blob_policy_scan`); and a worst-case rule for `P7.file_content_scan_worst` (a 2 MiB file with about 50,000 matches, and a Latin-1 file that decodes to 4 MiB with about 95,000, scan cache cold and blob cache warm, through the router), with what the server does above it. Indicative single-thread cost of the scan alone (a standalone build of `crates/engine/src/secret_scan.rs`, release, a 4-core sandbox, 17 Oct 2026; production has 2 vCPU): 19 ms for 2 MiB with no match, 53 ms for 2 MiB with 47,649 matches, 109 ms for 4 MiB with 95,294 matches. The last alone is above `P7.file_content_cold` (80 ms), and files of 200 kB do not show it. Each row has its own bench file and its own `[[bench]]`, and each commit that adds a row or flips `registered` also edits, in that commit, `crates/xtask/tests/budgets_registry.rs` (the threshold table and `REGISTERED`) and `registry_budgets` in the Justfile, because those gates fail otherwise. The existing rows `P7.file_content_cached`, `P7.file_content_cold`, `P7.compare_api` and `P7.text_search` keep their benches, extended to plant secrets in-process (the fixtures plant none), and are "measured with masking on". (`docs/interfaces.md` says `P7.compare`; that row is the engine's benchmark, and the registry's is `P7.compare_api`.)
14. **Order with 06.** The refusal of a write that holds a marker (`redaction_marker`, prompt 06) is not built. This prompt does not need it to start, but go-live needs both: until it lands, a client that posts the masked text of `getFileContent` to `editFile` overwrites the secret with its marker. The threat model says so.

### T2: The masker and the types that carry its output (S14b, S11, S22)

- A pure module in `crates/hub-registry/src/mask/`, with no I/O. `MaskedText` has no public constructor: it is made only by `mask::apply` and `mask::mask_lines`, which take a `Scanned { text, matches }` that only the scan cache builds from that same text. `apply(text, matches)` returns the masked text, the `masks` (at most 1,000, in start order, while the text is masked in full) and the replacement table. `mask_lines` does the same for the lines of one side of a diff. `remap_ranges` moves ranges through the table by binary search.
- All three are linear in text, matches and ranges (one forward pass with a monotone cursor over the text and the sorted matches, as the engine's `Columns::before` does) and total: a match that does not fit its text (a line past the last, a column past the line, overlap, not sorted, not on a character boundary) returns `Err(MaskError::Inconsistent)`, and the edge withholds, omits and counts, or compares by hash. They never panic (rule 2).
- Offsets are UTF-8 bytes of the masked text. A private key block gives one marker and one mask per line.
- The edge types in `http/dto.rs` (the file text, the served text, the lines of the comparison, the text of a hit) have type `MaskedText`. A missing scan result is a type error, never an empty list.
- Fuzz target `registry_masker`: its source in `fuzz/fuzz_targets/`, a `[[bin]]` in `crates/hub-registry/fuzz/Cargo.toml`, a corpus directory with at least the number of seeds `justfile_gate.rs` requires, a row in the crate's fuzz README, and its name in `registry_fuzz_targets`, all in this commit. Invariants: `text[start..end]` is a marker, boundaries fall on characters, offsets increase, no matched span survives in the masked text, the output length is bounded, and inconsistent matches give `Err`.

**Verify:** property tests `masks_name_exactly_their_markers` and `offsets_survive_non_ascii_text`; `apply_never_panics_on_matches_of_another_text`; a counted-steps test on a 2 MiB one-line non-ASCII text with 60,000 matches (the work at twice the input is at most 2.2 times the work at the input); goldens for CRLF, a lone CR, text decoded from UTF-16, a 27-line private key, 1,001 matches, and a source text that already contains a marker; `mask_types` (a source scan of `http/dto.rs`: no `String` or `Option<String>` field named `text`, `snippet`, `hunks` or `lines`, and no `serde_json::to_*` of a domain `FileContent`, `Comparison`, `ServedFile` or `TextResults` under `src/http/`); `LK_REQUIRE_DOCKER=1 just registry-fuzz` runs the target.

### T5: Compare (S14b; P7.compare_api)

### T6: Text search (S14b; P7.text_search)

- `search_text_masked(..)` runs the search, then maps each hit to its blob through the snapshot it searched (`snapshot.lanes[swimlane].list.files` holds path, class and hash, unsorted: build one map per request, bounded by the 1,000-hit ceiling), never through a fresh read; a hit whose swimlane and path are not in that snapshot is dropped and counted. It scans from `shard.contents`, the bytes the search ran on, through the `ScanCache`; maps the matches to the hit's line; masks the cut text; remaps `ranges`; and applies the closure of default 10.
