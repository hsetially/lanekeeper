# Threat model (STRIDE)

Each prompt fills in the section for the components it owns, and keeps it current. A human signs off before go-live (S24).

For each component, record:

- **Assets.**
- **Trust boundaries.**
- **STRIDE threats:** Spoofing, Tampering, Repudiation, Information disclosure, Denial of service and Elevation of privilege. Give each threat its mitigation, with the S# it maps to.
- **Residual risks.**

## Components

- Agent (02)
- Hub identity and audit (03a)
- Hub platform: gateway, routing, events, Git, webhooks (03b)
- Engine (04)
- Registry and read API (05)

## Contracts, ports, migrations, fixtures and fuzz skeleton (01)

Owner: prompt 01. This section covers what 01 creates and everything else builds on: the database roles and the audit table protections (`db/migrations/0001_init.sql`, `deploy/dev/init.sql`), the `Secret<T>` type, the typed validators (`NfsPath`, `RepoPath`, `CompareRef`, `GitRef`, `TenantId`, `PathMappingRule`), the proto and OpenAPI contracts, the synthetic fixture generator and the fuzz skeleton. Behaviour behind the ports belongs to the prompts that implement them and is covered in their sections.

### Assets

- The audit chain (`audit_events`, `audit_checkpoints`): the evidence of who changed what (S9).
- Secrets in memory: GitHub tokens, session ids, join tokens, webhook URLs, keys (S7, S8, S21).
- The NFS tree, which only typed paths may address (S11, S17).
- The two database roles, `lanekeeper_migrator` (owns the schema, runs DDL) and `lanekeeper_app` (the hub's runtime identity).
- The contract files themselves, which every other prompt trusts.

### Trust boundaries

- Hub process to PostgreSQL: the hub connects as `lanekeeper_app` and never as the migrator or a superuser.
- Network or API input to the typed validators: the first parse of every path, compare reference, tenant id and swimlane id.
- Agent and sentinel to hub over gRPC: message size limits and the join request shape live in `proto/agent.proto` and `crates/proto`.
- Developer machine and CI to the repository: fixtures are generated, never copied from a real environment.

### Residual risks

- **Owner-level database access.** The migrator owns the tables, so it can disable or drop the audit triggers. Mitigation is outside this prompt: the migrator credential is used only by the migration job, not by the hub, and the signed checkpoints (03a, S9) let a nightly job detect a rewrite. A rewrite after the latest checkpoint, at most one hour, is detectable only by the Cloud Logging copy.
- **Self-approval is guarded on insert only.** The `approvals_no_self_approval` trigger fires `BEFORE INSERT`. `lanekeeper_app` holds SELECT, INSERT, UPDATE and DELETE on `approvals` and `proposals`, so code running as that role (a hub bug or a compromised hub) can insert an approval by another user and then `UPDATE approvals SET approver_oid` to the author, `UPDATE proposals SET author_oid`, or `DELETE` a proposal (the cascade removes its approvals). Mitigation: approval enforcement (S4/D37) is also done in application code in prompt 06. Closing the gap (SELECT and INSERT only on `approvals`, a `BEFORE UPDATE` trigger on `approvals`, an author-immutability trigger on `proposals`) is a possible hardening for prompt 06 or a later contract-change. Accepted by a human at the round 3 review of prompt 01 (reword only).
- **The definer function is a privileged surface.** It is small and bounded. Anything that can call it as `lanekeeper_app` can drop sentinel partitions, but only whole months that ended more than 90 days ago (the floor is fixed in the function), plus default-partition rows older than 90 days; the audit tables are not touched, and deleting a sentinel does not cascade into its records. A caller can therefore make expiry happen when it is due and no earlier. It cannot make records last longer or shorter than the hub's own schedule decides above the floor. Lowering the floor is a migration and a recorded decision, not a runtime setting. Two limits remain: a caller can run the function repeatedly, which takes an advisory lock and briefly locks the parent table (a denial-of-service nuisance, not a data loss), and an owner-level credential is outside this control (see the first bullet).
- **`Secret::expose` is an escape hatch.** The type stops accidental formatting and serialisation, not a caller that reads the plaintext and logs it. Reviewers grep for `expose()`, and the log-capture tests of later prompts cover the paths that matter.
- **Rejection of unusual file names.** `NfsPath` rejects backslashes and control characters, so a real file with such a name cannot be addressed. This is deliberate (plan Q13); it surfaces as a finding rather than a silent skip.
- **A base file whose name ends in a known tenant id** is reported as a tenant file (plan Q14). This is a limit of the naming scheme, documented in `mapping.rs`.
- **Fuzzing coverage is a skeleton.** Three targets run 30 seconds each per smoke run. Parsers added by later prompts (YAML, `.properties`, Markdown chunking, webhook payloads, proto decoding at the hub) must add their own targets (S22).
- **The development database passwords** in `deploy/dev/init.sql` are for local use only; production roles come from CloudNativePG managed roles (09).

## Agent (02)

Owner: prompt 02. This section covers `crates/agent` as built by tasks T1 to T12: configuration and the cap-std root, joining the hub and renewing the certificate, the gRPC transport, the Merkle tree and scans, the durable spool, quiescence and sync tagging, deny globs, the config-server calls, file operations, the Kubernetes watchers and restarts, operations (health, metrics, logs), and the pod contract (`crates/agent/Dockerfile`, `HARDENING.md`, `RBAC.md`). The hub's side of the same links (issuing certificates, authorising commands, auditing) is 03a and 03b; the NFS VM sentinel is 17. The config-server calls (T12) are the agent's only use of an endpoint with no authentication (Q37), so they get rows of their own below.

The agent reports facts and carries out commands. It decides nothing: the hub checks the user's role, writes the audit event and sends the command. So this section asks two questions of the agent: can an outsider use it, and can a command from the hub do more than its shape allows?

### Assets

- **The client private key and certificate** (ECDSA P-256; the certificate lives 24 hours). They prove which swimlane the agent is (S5). The key is made in memory and stored only in the certificate Secret.
- **Join credentials:** the Google ID token for the agent's service account, and the one-time join token of the fallback (single use, valid 24 hours). Either one gets a certificate.
- **The NFS export of one swimlane** (`LK_NFS_ROOT`): the files the config-server serves. Integrity matters most, because a wrong byte is served to a bank's services. The files hold no secrets by design (D18), but keystores and keys may sit among them (D79).
- **The stream to the hub**, which carries file reads, writes, deletes and restarts.
- **The spool volume** (`LK_SPOOL_DIR`, a small persistent volume of its own, outside the NFS export): a copy of every version the scanner saw and the hub has not yet acknowledged, up to 512 MiB or 100,000 entries. It holds file content at rest, so it is as sensitive as the export. Integrity matters too: a version in it is sent to the hub as if the agent had just seen it.
- **The agent's Kubernetes access:** its service-account token, the Roles in `RBAC.md` (get, list and watch on Deployments, Pods and Jobs, and patch on Deployments, in the configured namespaces; get and update on the certificate Secret and get on the join-token Secret, both by name).
- **Cluster facts the agent reports:** Deployment and pod names, labels, environment variable names, and the values of the names on the hub's allowlist (D88).
- **Logs and metrics:** paths, hashes and ids, which must stay free of contents and secrets (S10).
- **Availability and freshness:** the agent's tree is how the hub learns of an out-of-band change within 15 seconds (P1).

### Trust boundaries

- **Agent to hub** (gRPC over TLS 1.3, one pinned CA, mutual TLS on the stream, no client certificate on `Join`). The hub is trusted to authorise commands. The agent still checks the shape of everything it receives, and clamps the settings the hub sends.
- **Agent to the spool volume.** Written and read only by the agent. What it reads back after a crash is untrusted: a cut or damaged file, or one that someone with access to the volume changed. Each record is checked (length, checksum, metadata) and then decoded and validated like a message from anywhere before it is sent.
- **Agent to the NFS export.** The export is written by others too: the config-server's jobs, the dataload Job, people on the VM. Everything under the root is untrusted input: names, symlinks, sizes, special files.
- **Agent to the Kubernetes API server** (service-account token, namespaced Roles). Responses are untrusted text and are trimmed on ingest.
- **Agent to the node's metadata server** (`169.254.169.254`, plain HTTP, node-local), for the ID token.
- **Agent to the config-server pods** (port 8888, plain HTTP, no authentication, Q37). The agent calls it in two ways only (a refresh and a served-file read, `src/configserver.rs`), each in answer to one hub command, and only at the address in `LK_CONFIG_SERVER_URL`. The NetworkPolicy contract limits egress to these pods on port 8888.
- **Container to node and cluster:** non-root, read-only root file system, no capabilities, RuntimeDefault seccomp, no shell, egress limited to five destinations (`HARDENING.md`).
- **Kubelet and Prometheus to the health port** (`9090`, plain HTTP, no authentication, three read-only paths).
- **Build to deployment:** the image is built from `crates/agent/Dockerfile` on digest-pinned bases with `--locked`; crates are exact pins (S19).
- **Chart and operator to the agent:** the environment variables are trusted configuration, validated at start.

### Residual risks

- **A deny glob decides by name, not by content (D79).** `*.pem` finds a key called `server.pem` and does not find one called `id_rsa`, `credentials` or `app.yml`, nor a password inside an ordinary config file. The built-in list is the one D79 names; the hub can add globs, and the secret scan on the hub (S14b) is the second line for values inside files. The agent cannot tell a key from its bytes without reading them, which is what the list exists to avoid.
- **Bytes that were spooled before a path became denied stay on the spool volume.** When the hub adds a glob, the pump strips the bytes from every record it replays, so they never reach the connection; but a record already written to a segment file keeps them until the hub has acknowledged it and the segment is deleted (mode `0600`, on the agent's own volume). The same holds for the hub: what it received before it sent the glob it still has, and marking a file denied does not change the Merkle root (the root commits to content, not to policy), so the hub is not told again about a file that does not change. Rewriting the spool on a change of globs would close the first part; it is not built.
- **The hash of a denied file is sent (D79).** The name, the size and the SHA-256 of the content go to the hub, because the hub must see that the file exists and that it changed. A hash lets whoever holds it check a guess of the content offline; for a random key that is no help, for a short password in a file it is. A `DENIED` answer carries no hash, so the hash is not available by commanding a write or a delete either.
- **Before the hub's first configuration only the built-in globs are in force.** A glob the hub adds applies from the moment its configuration is read (before the spool is replayed, and before the next command), and a walk is started at once to re-mark the tree; files the hub's own globs deny, and the built-in globs do not, are not denied in the first moments of a start. The built-ins are never absent.
- **A hub can deny files it should not.** A glob such as `*` makes every file denied: the agent then reports names, sizes and hashes only and refuses all commands on files. That is the hub choosing to see less, and it is bounded (1,000 globs of at most 512 bytes), but it is a way for a compromised hub to make the agent useless.
- **The spool is file content at rest.** Anyone who can read the spool volume (cluster administrators, the node) reads recent config, as they can read the export. Encryption at rest is a property of the volume, not of the agent, and the files are not encrypted by it. A file that no deny glob matches, whatever it holds, is in the spool too.
- **A damaged region costs the rest of its segment.** Records are framed without a resynchronisation marker, so a bad byte in the middle of a segment loses the records after it in that segment (up to 4 MiB) and not just the one it is in. The loss is reported, and the hub's root comparison recovers the state; the intermediate versions are gone.
- **A version can be sent twice.** Delivery is at least once: after a crash, the acknowledgements of the last second may not have been written down, and a delta whose acknowledgement was in flight is sent again with the same sequence number. The hub applies a delta by hashes, so a repeat changes nothing, but a hub that records an event per delta must deduplicate by sequence number.
- **A full or failing volume loses versions, not the agent.** If the volume is smaller than `LK_SPOOL_MAX_BYTES`, or fails, an append fails (`ENOSPC`, I/O error): the delta is not spooled, the segment is abandoned, and the hub learns of the change through the heartbeat root and a `RequestDelta`. The chart must size the volume above the byte bound. Appends sit in the path of P1, so a slow volume delays every delta by its fsync.
- **A hostile writer can push history out.** Someone who can churn files on the export fills the spool faster than the hub can drain it during an outage, and the oldest whole deltas go first. The gap says so; the last state is never lost, because the tree and the heartbeat root are not in the spool.
- **A gap waits for a delta to ride on.** The loss is stamped on the next delta sent. With an empty spool and nothing changing, it waits; the hub sees the root mismatch meanwhile and asks for a full scan.
- **The hub is trusted to authorise.** A compromised hub, or an agent certificate stolen within its 24 hours, can read any regular file of at most 2 MiB under the root, write or delete one against its current hash, and restart any Deployment in the configured namespaces. The agent bounds what a command can be (typed paths, hash, size, namespace) but does not decide whether a command is wanted. The agent has no revocation list; ending a stolen identity is the hub's job (03b).
- **Key and token material cannot be wiped everywhere.** The agent wipes its own copies, but the key's bytes pass through hyper, kube, rcgen and TLS library buffers that it cannot zeroize. The Kubernetes client deserialises whole Deployments, environment values of variables that are not allowlisted included, before they are trimmed away; those strings are dropped, not wiped. The certificate Secret holds the private key in the cluster: anyone who can `get` that Secret (cluster administrators) or read the node's memory or disk can take it, and encryption at rest is a property of the cluster.
- **A join token cannot be renewed (token-only clusters).** The fallback token is single-use. If the agent loses its stream and cannot renew over it before the 24-hour certificate runs out, the re-join has no valid token, and the agent stays disconnected (`/readyz` fails) until an Admin issues a new one. Clusters with Workload Identity re-join on their own. This follows from Q26.
- **A renewed certificate reconnects the stream.** The session reconnects when the outbox is empty, or after 30 seconds at most. A command that is running at that moment gets no reply, and the hub times it out.
- **`verify` does not check the chain's signature.** `ClientIdentity::verify` checks the key, the SAN, the lifetime and the parse. The signature is checked by the TLS handshake (the hub checks our certificate against its CA on every stream), not at join.
- **NFS has no compare-and-swap.** Between the hash check and the rename, another writer on the export can change the file, and a replace or a delete then overwrites that change. The window is one rename. Creates are protected (hard link). The sentinel (17) is what shows who else wrote.
- **A file swapped for a FIFO can block a thread.** If a regular file is replaced by a FIFO between the `lstat` and the `open` (the walker and file operations both have that window), the `open` blocks until something opens the other end. The caller of a file operation gets `IO` after 30 seconds, but the blocked thread, and the lock stripe it holds, stay stuck until then; the walker's thread would stall the scan until `/healthz` fails after 11 minutes and the kubelet restarts the container. Sixteen blocking threads exist. This needs write access to the export and good timing; there is no `O_NONBLOCK` guard. This was found by reading the code and is not covered by a test.
- **Leftovers and hidden names.** A crash between staging and renaming leaves a `.lanekeeper-tmp-*` file that nothing sweeps. The walker ignores names that start with `.lanekeeper-tmp-` or `.nfs`, so anyone with write access can hide a file from the hub by using such a name. New files are mode 0644 and owned by the agent's uid; whether the config-server can read them depends on `root_squash` and the uid (Q11, 1010 by Q4), which must be settled before the agent writes on a pilot swimlane.
- **Symbolic links are invisible to the hub's commands.** A link is never followed, even inside the root, so a config file that is a link is reported as an entry the hub can neither read nor write. This is deliberate (S17).
- **A write racing a long scan.** A tool write that races a scan longer than 2 seconds may push one extra delta. It is harmless: the next walk finds the file unchanged.
- **The service-account token is mounted.** The agent needs the Kubernetes API, so anything running in the container can read the token. There is no shell and no second process, but a Role cannot limit `patch` to one annotation: a stolen token could patch the image or command of any Deployment in the configured namespaces.
- **The Kubernetes link is the client library's.** It uses rustls with aws-lc-rs and verifies the cluster CA, but the kube client also accepts TLS 1.2; only the hub link is forced to 1.3 (S6). A watcher whose list keeps failing retries with backoff for ever, logging only the HTTP status; the cluster report then stays "not synced".
- **Plain-HTTP hops.** The metadata server (node-local) and the config-server (Q37, no authentication) are reached without TLS. The NetworkPolicy contract limits who can be reached; it does not make the hop private. The config-server accepts a refresh from any pod that can reach port 8888, not only from the agent; that is a property of the endpoint, and its NetworkPolicy belongs to the chart.
- **A deny glob decides `FetchServed` by the names in the request.** The agent checks the file as named, with the application's folder, with the channel's folder and with the tenant's copy. The config-server also searches every other directory, so a file whose only denied part is a folder the request does not name (`private/app.yml` when the request is for `app.yml`) is not found by the check. Keystores are caught by their extensions wherever they sit; a hub glob that names a folder is not. The bytes of an unlisted file the server resolves are returned as the server serves them.
- **A refresh may be applied twice.** A refresh that timed out may have been applied; it is tried again (up to three attempts). A refresh is safe to repeat, so this costs a second reload at most.
- **The config-server's status is passed on as given.** A `2xx` is the hub's to read as success; the agent does not judge it. A server that answers `200` and did nothing is not noticed.
- **The start time is the oldest pod's.** `config_server_started_at` is the earliest start among the config-server Deployment's pods, so a replica that predates a folder is not hidden by a newer one. A delta that does not mention the Deployment carries none, and a Deployment with no started pod reports none, so the hub keeps its last value.
- **The log filter cannot prove a negative.** The Kubernetes client crates are silenced and other libraries are held at `warn`, but nothing proves that no other library ever logs text that the hub or the cluster chose. The agent's own logs hold file paths, which an NFS writer chooses; JSON escaping keeps them to one line.
- **The pod contract depends on the cluster.** The image build has not run (no Docker daemon where this was written), a NetworkPolicy is ignored by a CNI that does not enforce it, the metadata address and port are placeholders until a real node confirms them (Q26), the hub and API-server CIDRs are values the chart fills in (Q1), and the health port is unauthenticated. Base-image digest pins receive no fixes until someone changes them, and there is no signature or SBOM check on the image (09).
- **A hung NFS mount is noticed late.** File operations time out after 30 seconds, but `/healthz` fails only after the scanner has made no progress for 11 minutes.
- **A stale cluster delta after a reconnect.** A delta that was blocked in the 8-slot report channel while the hub was away can be sent after the full report that follows the reconnect, and then stays stale until the next change or the next report request.

- **Anyone who can create a Job in a watched namespace can open a sync window.** A Job whose name matches `LK_SYNC_JOB_NAME_GLOBS` (default `*dataload*`) or carries the configured label opens a window; changes seen while it runs are tagged with it, and the hub holds drift alerts until it closes (D75). A Job that never finishes would keep them held. The agent does not bound the length of a window: the hub (05) must, and must show a tag from a window that is older than the Job's normal run as such. Namespace write access is already trusted with the export's content (the dataload Job writes it).
- **Quiet is estimated from file times.** The quiet period counts from the newer of a changed file's mtime and ctime, read from the NFS server and compared with the agent's clock; a skew of seconds makes a batch go out early (more deltas, never a lost change) or up to that much later (P1 has about 2 s of headroom beyond the worst case). A removal has no time and counts from the walk that saw it.
- **A change hidden by attribute caching is tagged late or not at all.** If the NFS client caches attributes, a walk can miss a file written during a window until the cache expires or the 15-minute full rehash finds it; the window's close may then already have been sent, and the delta arrives untagged. The hub sees it as out-of-band drift (a false alert, not a missed one).
- **Window events are not acknowledged.** A close lost with a connection is repeated on the next one, for an hour; a hub that was away longer does not learn of it, and a window it holds open must be bounded by the hub.

## Hub identity and audit (03a)

Owner: prompt 03a. This section covers `crates/hub-identity` as built by tasks T1 to T5: Entra sign-in for the web UI (T1), users, roles and access requests (T2), sessions and CSRF (T3), default-deny authorization and bearer-token verification for MCP and agent join (T4), and the hash-chained audit log with its KMS-signed checkpoints, nightly verification and Cloud Logging copy (T5). The crate is a library; the hub binary (09) composes it, supplies the real `SecretSource`, `KmsSigner`, `Notifier`, `EventBus` and `Leases`, and runs `hub_identity::testing::assert_hub_route_table` against its full route table. The tables and the append-only trigger belong to 01 (see that section); the agent gateway, certificate issuing and the Git mirror are 03b; MCP tools are 07; the vault for GitHub tokens is 06.

The crate answers two questions. Can someone become a user, or a role, they were not given? And can what the users did be changed afterwards without anyone noticing?

### Assets

- **Sessions.** The cookie `__Host-lk_session` carries 256 random bits; the table holds only their SHA-256. Whoever holds the cookie is that user until the session ends (S2).
- **The CSRF token.** The cookie `__Host-lk_csrf` carries a second random value, and the session row holds its hash. It is what makes a state-changing request deliberate (S3).
- **Login state.** The sealed cookie `__Host-lk_login` (state, nonce, PKCE verifier, return path, 10 minutes) and the 32-byte key that seals it, held in Secret Manager and shared by the replicas (S1, S7).
- **The hub's credential to Entra.** A federated assertion (the projected service-account token, read on every exchange) or a client secret from `SecretSource` (S7, Q25).
- **Bearer tokens in transit.** Entra access tokens for MCP and Google ID tokens for agent join. Each is a credential until it expires (S1).
- **The user directory.** Roles, status and the `requires_approval` flag decide every authorization (S1, S4). The list of bootstrap admin object ids in the configuration decides who starts as Admin.
- **The trust anchors fetched at run time:** the discovery document and the signing keys (JWKS) of Entra and Google, the checkpoint public key (configuration), and the cached copies of all three.
- **The audit chain.** `audit_events` and `audit_checkpoints`, the checkpoint objects in the locked bucket, the KMS signing key's use, and the Cloud Logging copy. Together they are the evidence of who changed what (S9).
- **The chain lock.** One advisory lock serialises every audited transaction from `record` to commit, so availability of the lock is availability of every write.
- **Logs and metrics,** which must stay free of tokens, cookies, secrets and event contents (S10).

### Trust boundaries

- **Browser to hub.** Everything in a request is untrusted: cookies, headers (`Origin`, `X-CSRF-Token`, `X-Request-Id`), the query of the callback, the return path, JSON bodies. The edge parsers are strict and bounded, and a request carries no authority until the session lookup says so.
- **Hub to Entra and Google** (TLS 1.3 only, one HTTPS client with a host allowlist). Discovery documents, key sets and token responses are untrusted until they pass the checks; no URL is ever taken from a token.
- **Holders of bearer tokens** (MCP clients, agents) **to hub.** The token is checked in full before anything else is read from it.
- **Hub replicas to PostgreSQL,** as `lanekeeper_app`, which holds INSERT and SELECT only on the audit tables (01). Replicas learn of each other's role and status changes through the outbox event, not through shared memory.
- **Hub to Secret Manager and to the projected service-account token file.** The only secrets this crate reads. It has no Kubernetes client.
- **Hub to the checkpoint bucket and to KMS.** Through the GKE metadata server (plain HTTP on a link-local address, node-local) and `KmsSigner`. The hub may create objects and request signatures; it cannot overwrite or delete a checkpoint object (locked retention, create-only upload).
- **Hub to the notifier,** after the commit and with a timeout. It carries a name and a link, and a failure never rolls back the action.
- **Database owner to the audit tables.** The migrator (and anyone with the owner role) can disable the trigger. That is the boundary the checkpoints and the Cloud Logging copy exist to watch (S9).
- **This crate to the hub binary.** The crate guarantees what it registers. The binary must register every other route through the same guard and run the exported checks (S4).

### Residual risks

- **Session lifetime.** A session is valid for 8 hours idle and 12 hours absolute (S2). A stolen cookie (a compromised browser, malware, script injected by a flaw in the web app) is a full session until it ends; there is no device binding. The cookie is `HttpOnly`, `Secure`, `SameSite=Lax` and `__Host-` prefixed, which stops the common routes, not an attacker on the user's machine. The web app's CSP and Trusted Types (08, S12) are the defence against script injection.
- **Idle precision and cache staleness.** `last_seen_at` is written at most once a minute and flushed in batches, and the cache adds up to 30 seconds, so the 8-hour idle limit is accurate to about two minutes. A replica cut off from both PostgreSQL and the event stream can serve cached sessions, with the roles they had, for up to 30 seconds before the cache expires; the cache switches off only once the end of the stream is seen.
- **Delayed lockout from Entra.** A user disabled in Entra keeps a session until an admin disables them in the app or the session ends (at most 12 hours); Entra is asked only at sign-in. Over MCP a token is a bearer credential until its expiry, but the user's status in the app is read on every call. Disabling in the app is immediate on the web and over MCP.
- **Login state is single use only because Entra says so.** There is no server-side record of a used login (decision B3, no new table). A captured callback URL cannot be replayed because Entra rejects a reused code and the nonce must match the cookie, but the hub itself does not remember. A leak of the login-cookie key (Secret Manager) would allow forged login cookies, not sessions: a valid code and ID token are still needed. Rotating the key ends logins in progress.
- **No rate limit on the sign-in routes.** Inputs are bounded and every outbound call has a timeout, but nothing here limits how often `/auth/login`, `/auth/callback` or `/auth/logout` are called by one client. Entra throttles its own side; the ingress or WAF (09) must limit the rest. Access-request spam is limited by the cooldown.
- **The chain lock serialises audited writes.** Every audited transaction waits from `record` to commit, so a caller that does slow work after `record` stalls all writes, and a wait over 5 seconds fails the action (closed, not open). The contended benchmark measured the extra cost of `record` at a p95 of 2.4 to 3.1 ms over 8 runs against the 3 ms budget of `P12.audit_record` (about 2.0 ms with fsync off); a human accepted that range and the budget stays at 3 ms. Writes are human-paced (tens a minute at design scale), so this is a latency cost, not a throughput limit. The registry's replay ingestion audits many paths with `record_many`. Like `record`, it holds the lock from its acquisition to the end of the caller's transaction, so a transaction that makes several batches holds it for all of them, and a caller keeps its transaction short. The work one batch adds is bounded by 200 events and 1 MiB of canonical JSON: measured in a release build on a 4-vCPU VM with Postgres 16.15 on the same machine, other builds running, the lock is held for 19 to 39 ms behind 3 events at the budget, 26 to 58 ms behind 200 events at the budget and 3.4 to 15 ms behind 50 typical events, against 5 s for the other writers' lock timeout (a debug build takes about 80 ms at the budget).
- **Tamper evidence has a window.** The nightly job starts from the rows in the table. A tail cut off after the newest checkpoint (at most an hour of history), or an event removed together with its checkpoint rows, leaves a chain that is consistent in itself; the bucket objects and the Cloud Logging copy are the evidence then, and nothing automatic compares them. Rolled-back transactions leave gaps in `seq`, which the verifier tolerates and follows by hash, so a gap alone is not a finding. Two limits of the nightly check are known and left to a human decision: it looks at a bucket object only for a checkpoint row that exists, so an owner who cuts the tail and also deletes the matching `audit_checkpoints` rows gets a clean run (a bounded prefix listing of the bucket would close this); and the copied columns are compared with the stored text only for rows whose hash is good, and `seq` and `recorded_at` (server time, not copied from the event) are not compared. Round 3 left one more limit, which stays: `created_at` of a checkpoint row is not compared with the bucket object's copy. The three limits that round 3 recorded about a repeated `seq` (missed across a batch edge), about the size of a `jsonb` column (measured by printing it) and about a run that ends `Errored` raising no notification are closed in round 4, the last with a limit of its own (the next bullet). The record of the second was wrong about the cost: printing 9,000 numbers of `1e131000` makes the server refuse the conversion, and those are 2.5 KB stored, so the INSERT-only role could end every run with one row (see the `jsonb` row of the STRIDE table). Round 4 leaves these, all known: a position held by more rows than a batch (5,000 by default) is reported as repeated but compared only as far as a batch reaches into it; the order of rows that share a position is not promised, so a report may name a broken link beside a repeated position; and the statement timeout runs while the client compares a chunk (harmless for legitimate rows; a batch of hostile rows near the size limit was not measured against it).
- **The count of nights without a verdict is in memory, and an alert may never fire.** The job counts the nights in a row that ended in an error (or in a run that found something and could not finish) and alerts from the second. The count is held by the job, because the `Leases` port holds no payload and `db/migrations/` is a contract path: a restart of the pod, or the lease passing to another replica, starts it from zero. With a pod that restarts daily, or two replicas that take the lease on alternate nights, and a verifier that fails every night, the count never reaches two and this alert never fires. Operations must therefore also alert from Prometheus on `increase(audit_verify_errors_total[3d]) >= 2` and on `increase(audit_verify_runs_total[36h]) == 0 or absent(audit_verify_runs_total)`, which read history that survives restarts (expressions and the gauge are listed in `metrics.rs`). A durable count needs a human-approved contract-change PR that adds a table `audit_verify_state (id boolean PRIMARY KEY DEFAULT true CHECK (id), unfinished_runs integer NOT NULL, last_error text, updated_at timestamptz NOT NULL)` with one row, granted `SELECT, INSERT, UPDATE` to `lanekeeper_app`, written in the verifier's own transaction after each run. Until then the limit stands. An error that is a refusal of the shape of the tables does not wait for the count: it alerts the night it happens.
- **An owner can blind the verifier without making a query fail.** The nightly job reads `audit_events` and `audit_checkpoints` by unqualified name, as the application role, and trusts what the database returns. An owner, or a role that can create objects in a schema ahead of the role's `search_path`, can put a view named `audit_events` in front of the table, add a row-level-security policy that hides rows from `lanekeeper_app`, or add a rewrite rule; none of these makes a query fail, and this job does not detect them. Rows hidden from the middle of the chain break the next link and are found; a tail hidden from the verifier is the window described above. A different case is found: `ALTER COLUMN ... TYPE <same family> USING <expression>` rewrites a copied column without firing the append-only trigger, and the column then no longer equals the stored event, so it is a `ColumnsDiffer` finding. Everything in this paragraph needs an owner, who can also drop the trigger and the verifier, so the defence is outside this crate: the checkpoints in the locked bucket, and an alert on DDL by the owner role (database audit logging), which belong to the deployment. A cheap hardening that is not done here is `SET LOCAL search_path = pg_catalog` in the verifier's transactions and schema-qualified table names (round 5 review, non-blocking item 1).
- **A compromised hub can write false history, not erase it.** The hub's service account may request signatures and create bucket objects, so a compromised hub can append false events and sign a checkpoint for them. It cannot replace an existing object or edit signed history. The KMS key's IAM, the bucket's locked retention and the separation of the migrator credential are the controls (09). An owner who also controls the signing key path could forge a chain; this is not defended here.
- **Not everything is audited.** A failed sign-in, a rejected token, an expired-session sweep, a `last_seen_at` write and a cache eviction are maintenance or refusals, not state changes (B19). They are logged by variant and, where useful, counted, not written to the chain. A burst of failed sign-ins is visible in logs, not in the audit log.
- **The Cloud Logging copy lacks the diff.** The line has the diff's SHA-256 and length, not its text (B8, S10), and it lags the commit by up to 5 seconds and is delivered at least once, so a restart repeats at most an hour of lines. A diff rewritten in the table cannot be compared with a copy of the original text, only with its hash.
- **Bootstrap admins and recovery.** The configured object ids become Admin at their first sign-in only. If every admin is later disabled or removed, recovery is a database intervention by the owner (B13); that is deliberate, since a standing break-glass rule would be a way in. The list is trusted configuration.
- **Display text is attacker-chosen.** The email and name come from claims and are shown to admins and in notifications. This crate trims them for the notification and never uses them for identity; escaping them is the web app's job (08).
- **Guard coverage depends on the binary.** The crate guarantees the routes it registers. A route that the hub binary adds without `GuardedRouter` is caught only if the binary runs `assert_hub_route_table` and `assert_default_deny` on its full table; MCP tools are guarded by 07 through `McpAuthenticator`. Until 09 wires the checks, the guarantee covers this crate's routes alone. Admin writes also have no `Idempotency-Key` layer here (B17): approve and reject answer 409 on a repeat and an update that changes nothing writes nothing, which makes a repeat safe.
- **Checked against fakes, not the real services.** Entra's federated credential from the GKE issuer (Q25, B18), the real v2 token shape and key rotation, Cloud KMS signing, a locked GCS bucket and the GKE metadata server were not available to the tests; the mock provider, a test P-256 key and in-memory bucket stand in. The metadata server speaks plain HTTP on a link-local address, and the NetworkPolicy and the pod boundary are what protect that hop. An Entra app registration that issues v1 access tokens is refused (fail closed). Real-tenant and staging checks belong to the go-live sign-off (S24).
- **Fuzzing needs the pinned nightly.** The seed corpora are replayed on stable in every `cargo test`, but the 30-second libFuzzer runs (`just identity-fuzz`) need the pinned nightly toolchain and cargo-fuzz, and the nightly 10-minute runs are CI's job (S22).
- **The token library is ours to keep right.** The prompt names `openidconnect`; its release depends on `rsa` with the open advisory RUSTSEC-2023-0071 and brings a second crypto stack, so the flow and the RS256 verification are hand-written here, directly on `aws-lc-rs` (`parse_compact`, `verify_with_keys` and `check_claims` in `oidc/jwt.rs`, with the key set in `oidc/jwks.rs`). The approved plan's B1 choice was `jsonwebtoken` on aws-lc-rs; T1 replaced it, because it adds a provider switch that panics when none is installed, and that replacement needs a human to confirm (B1). Every check is in this crate's code and has a named test, but a flaw in them is ours, not a library's.

## Hub platform (03b)

Owner: prompt 03b. This section covers `crates/hub-platform` and `crates/hub` as built by tasks T1 to T11: the composition and its headers, limits, static files, operations and shutdown (T1); the Google clients for Secret Manager, Cloud KMS and Workload Identity (T2); the agent CA, `Join` and `Connect` (T3); multi-replica routing and the replica `Forward` RPC (T4); the event bus and Server-Sent Events (T5); leases and singleton jobs (T6); the Git mirror, tree index and webhooks (T7); the blob store and blob endpoint (T8); the transactional outbox (T10); and the sentinel endpoint, acknowledgements and pull-request webhooks (T11). Identity and sessions (who the user is, roles, CSRF, the audit chain) are 03a; what the registry decides (denied and withheld files, drift) is 05; the sentinel daemon is 17; the chart and the network that surrounds the pods are 09.

The platform is the runtime everything else sits on, so it asks two questions: can an outsider (a browser, an agent, GitHub, another pod) make it do something it should not, and can one component of the platform (a replica, an agent, a user) reach what belongs to another? A row's Proof cell names tests, benchmarks or fuzz targets that exist in `crates/hub-platform` or `crates/hub`; `tests/threat_model.rs` fails if one does not, or if the name is a helper and not a test. A control that is planned but not built has a Proof cell that starts with `None` and says which task adds it, and that task replaces the cell with its tests; after T11 no row is left with one.

### Assets

- **The CA signing keys.** By design two Cloud KMS keys (plan A7): one for agents, sentinels and the hub's server certificates, and one for replicas. The private keys never leave KMS and the hub never loads one: every signature is a call to `KmsSigner::sign_digest`. Whoever can use these keys can mint an identity (S5, S6).
- **The CA certificates** (public). The hub checks at start-up that the certificate's key is the one KMS signs with, and refuses to start on a mismatch.
- **Issued certificates and their keys.** An agent's or sentinel's private key lives with the agent (the hub sees only a CSR). The hub's own server and replica keys are generated in memory at start-up, signed through KMS, valid 24 hours and renewed at half their life. No certificate or key of the hub is stored anywhere.
- **Join credentials.** The Google ID token of an agent's or sentinel's service account, and the one-time join token of the fallback (stored only as a SHA-256 hash, single use, valid 24 hours).
- **Runtime secrets.** The GitHub webhook secret, the read-only Git credential, the Workload Identity access token and the database URL. They are `Secret<T>` (redacted, zeroized on drop), read from Secret Manager through a five-minute bounded cache or, for the Git credential in Q17's interim, from a mounted file.
- **The agent connection table** (`agent_connections`: swimlane, replica, address, epoch, last seen) and the streams it points to. A command written to the wrong stream is a write to the wrong swimlane's NFS export.
- **Commands and replies in flight.** They carry file content and hashes between a user's request, a replica and an agent.
- **Events** (the `outbox` table and the SSE streams): ids and hashes of what changed. They decide what a browser refetches, so a lost or forged event is a stale or misleading screen.
- **Blobs** (`blobs`: content-addressed config bytes, up to 4 MiB each) and the blob cache. The files hold no secrets by design (D18), but keystores, keys and withheld files exist among them (D79).
- **The Git mirrors** (one bare repository per kind on each replica's volume) and `git_tree_index`: the hub's copy of both repositories, all branches and tags.
- **The leases** (`leases`): the decision of which replica runs each singleton job.
- **The database connection** as `lanekeeper_app`, over verified TLS.
- **Logs, traces and metrics**, which must stay free of contents and secrets (S10).
- **Availability.** Three replicas behind two load balancers; an agent attached to any of them; the freshness budgets (P1, P2, P13) depend on this runtime.

### Trust boundaries

- **Browser to the web listener** (HTTPS behind the users' load balancer, TLS 1.3 only at the hub, D25). The hub does not trust the request: every route is registered with a declared guard (S4), resolved through the `SessionAuth` seam to an active user, and the request passes the headers, limits and drain layers first. Who the user is belongs to 03a.
- **GitHub to `POST /hooks/github`**, the one HTTP route with no session. The proof of origin is an HMAC over the raw body with the webhook secret. A source-address allowlist at the load balancer is the other control (S18, Q28, 09); the hub does no address check.
- **Agent to the agent listener** (gRPC over TLS 1.3, mutual TLS, client certificate optional at the TLS layer so that `Join` can run without one). Every other RPC takes the identity from the verified peer certificate: `spiffe://lanekeeper/swimlane/<id>` for an agent and `spiffe://lanekeeper/sentinel/<name>` for a sentinel, and one is never accepted for the other's RPCs. Nothing in a message is trusted for identity.
- **Replica to replica** (the `Forward` RPC, on its own listener with its own TLS configuration that trusts the replica CA and nothing else). A replica's identity is `spiffe://lanekeeper/hub/<replica>`; peers are found through the address each replica wrote itself into `agent_connections`.
- **Hub to Google** (`*.googleapis.com` over TLS 1.3 with verified certificates, and the node-local metadata server over plain HTTP). The hub calls three REST methods through its own small client with a host allowlist, a response cap, a timeout and no redirects.
- **Hub to GitHub** (HTTPS through `gix`, whose transport is `reqwest` on rustls with aws-lc-rs, read-only credential, 30 s per request). Everything fetched is untrusted until the typed parsers have read it.
- **Hub to PostgreSQL** (TLS with `verify-full` against the CA file in the settings, always, whatever the URL says; the hub connects as `lanekeeper_app`).
- **Hub to Cloud KMS.** IAM on the two CA keys is the root of trust for every certificate in the system, replicas included (plan A18).
- **Platform to the ports that others implement**: `SessionAuth` and `TokenVerifier` and `AuditLog` (03a), `BlobPolicy` and `ReportSink` (05), `SentinelSink` (05 and 17). The platform trusts them to decide, and none of them has a fallback to a fake in the binary.
- **Prometheus and the kubelet to the operations listener** (plain HTTP on a cluster-internal port: `/healthz`, `/readyz`, `/metrics`, GET only, no secrets).
- **Container to node and cluster.** Non-root, read-only root file system, no capabilities, RuntimeDefault seccomp, no shell, egress limited by the NetworkPolicy contract in `crates/hub/HARDENING.md` (S16, S18).
- **Build to deployment.** Digest-pinned bases, `--locked`, exact crate pins at least 14 days old, `cargo deny` and `cargo audit` over the main lockfile and the platform's own fuzz lockfile (S19).

### Residual risks

- **The blob endpoint depends on a policy that 05 supplies, and a hash is a capability.** `GET /api/v1/blobs/{hash}` asks a `BlobPolicy` (an `async` trait: the registry's answer needs its own queries) before it reads the store. The only implementation in this repository is the test double `DenyHashes`, which is not compiled into a release build, and the binary refuses to start without the real identity module and registry, so until 05 lands no deployed hub serves a blob. Once it does, "denied or withheld" is exactly as complete as 05's decision (D79). Roles are global (D35), not per swimlane, so any active user at Viewer or above who knows the hash of a blob that is not withheld may fetch it whichever swimlane it came from. The policy call is awaited inside the request, so the 30 s request timeout bounds a slow policy, and a policy that errors must fail closed (05's to prove).
- **Readiness of the mirrors is "holds a branch", not "is current".** `MirrorsReady` is the readiness check that fails `/readyz` until `Mirror::initialize` has filled an empty volume, so no read that needs a commit is routed to a replica that cannot answer. A mirror that has stopped fetching (a lost credential, an unreachable remote) stays ready; the signals are the webhook and poll outcomes and the fetch metrics, not readiness. A replica started on an empty volume while GitHub is down is not ready and takes no traffic until its first full fetch succeeds (bounded by `LK_GIT_FETCH_TIMEOUT_SECS`).
- **Buffers that hyper owns cannot be wiped (S7).** `Secret<T>` is redacted, zeroized on drop and compared in constant time, and the hub wipes the copies it controls (`GoogleResponse::wipe` overwrites an answer that carries a secret or a key when nothing else holds the bytes). The same bytes also pass through hyper, tonic, axum, rustls and prost buffers, reference-counted `Bytes` that are freed without zeroing: a join token inside a decoded gRPC frame, a bearer header, a Secret Manager answer or the webhook secret may stay in freed heap memory until it is reused, and a webhook body is read as plain bytes. Reading it needs access to the process's memory (a debugger, a core dump, the node); the pod has no shell and no capabilities (S16), and an administrator of the node is outside this model. This is the same limit the agent records for its key material.
- **Replica trust rests on KMS IAM on the replica CA key (A18).** Every replica signs its own certificate at start-up with the replica CA key, so "this is a hub replica" means "this process may use that key through Workload Identity". Anyone who can call `asymmetricSign` with that key can mint a replica certificate and forward commands to any agent stream, and the replica listener checks the SAN prefix but cannot tell a real replica from such a holder. The IAM binding on the replica CA key must go to the hub's service account alone and nothing else (09), and an audit log of KMS data access is the detection. The agent CA key has the same property for agents, with the 24 hour and ID-token limits above.
- **A stolen agent key is good for its 24 hours, and there is no revocation list.** A certificate is valid until it expires; the hub's controls are the short life, renewal only over the agent's own stream or a fresh join, the audit event for every issue, and disabling the swimlane's registered service account, which stops renewal. A stolen key can read and write that agent's NFS export within what the agent allows (typed paths, hashes, size caps) until then. Token-only clusters cannot rejoin without an Admin issuing a new token.
- **`POST /hooks/github` is the one unauthenticated HTTP route.** The controls are in the hub: the body cap, the HMAC over the raw bytes checked first and in constant time (a bare 401), the event type, the replay guard in Postgres, keyed on the HMAC of the body (the keys are pruned after seven days, so a capture replayed after that is accepted: for a push it costs one coalesced fetch, and for a `pull_request` it re-applies that event's action to its link, where `merged` stays terminal and nothing orders events by time; two deliveries whose bodies are byte for byte the same are one delivery to the guard, which GitHub is not expected to produce for distinct deliveries, as its bodies carry commit ids and timestamps; the cost of being wrong is one dropped duplicate, and the 60 s poll covers a push), a strict typed parse, and a bounded and coalesced fetch queue so a flood of valid deliveries cannot cause unbounded fetches. The source-address allowlist at the load balancer is the other control (S18, Q28), and it is 09's: the hub does no address check, so without it anyone who holds the secret, or who can flood the route with unsigned bodies up to the cap, reaches the HMAC step. A leaked webhook secret lets a holder trigger fetches and `GitHeadMoved` events for configured repositories only, never choose what is fetched. A push larger than the 1 MiB cap is a 413, and the 60 s poll picks the change up within 75 s.
- **`gix` brings `reqwest` and a wider dependency graph (A16).** The only `gix` HTTPS transport on rustls with aws-lc-rs is `reqwest`, so `reqwest`, `hyper-rustls` and `rustls-platform-verifier` are in `Cargo.lock` as `gix-transport`'s HTTP client; no crate of ours depends on `reqwest` or calls it. A human accepted this at the A16 gate (`plans/03b-hub-platform.blockers.md`) and chose to narrow the `[graph]` of `deny.toml` to the two Linux targets, so that `webpki-root-certs` (CDLA-Permissive-2.0, a wasm32-only dependency) is no longer checked. The cost is that `cargo deny` no longer checks the Windows and macOS dependency graphs, which no shipped binary uses; `cargo tree -i ring` for the hub-platform crate prints nothing. The normal graph of `hub-platform` grew from about 260 to about 410 unique crate versions, each pinned at least 14 days old and under `cargo audit`.
- **The hub binary has `ring` through `sqlx` for the database leg (A15).** The `sqlx` variants whose TLS is aws-lc-rs pull `webpki-roots` (CDLA-Permissive-2.0, which `deny.toml` does not allow), so the hub uses `tls-rustls-ring-native-roots`: the database connection is rustls on `ring`, while every listener and client the hub builds itself is rustls on aws-lc-rs. Two crypto providers are linked into one binary. The pool is always built with `verify-full` and the CA file from the settings (`sslrootcert`), whatever the URL says, so the platform roots that the feature name mentions are not what decides trust; this is proven against a Postgres with a wrong CA (`pg_pool_refuses_wrong_ca_and_wrong_host_name`) and would need a re-check on a `sqlx` upgrade.
- **`git_tree_index` has no retention.** The leaseholder writes the index of every branch head and tag commit once (one row per file of the commit's tree), and nothing deletes rows (D78 keeps versions but names no limit for this table), so the table grows with every commit pushed and every tag, by the number of files in the tree each time. The cache in memory is bounded by entries, but the table has no prune job and no partitioning, so disk and the cost of the indexes grow without a ceiling. A retention policy needs a decision (keep the heads, the baselines and the last N commits?) and is not made here; it is the first thing to settle before the repositories have a long history.
- **The Git client trusts the system roots and has a 30 s total timeout per request.** `gix`'s `reqwest` transport verifies GitHub's certificate against the platform's root store (it ignores `http.sslCAInfo`), so any root that the image's trust store holds can vouch for the remote, and the hub cannot pin GitHub's issuer; the distroless base carries Debian's CA bundle and receives fixes only when its digest is bumped. The transport's total timeout is 30 s for each request, a limit of the client that the hub cannot change, so a very large first fetch of a big repository over a slow link is made of requests that must each finish in 30 s; the hub's own deadline (120 s by default, plus a 45 s grace) bounds the whole fetch and a failure leaves the work to the next poll. The credential is only ever offered to the host the URL names.
- **Outbox rows and events are not content, but they are metadata.** An event names a swimlane, a path hash and a kind, and any active user at Viewer or above who may see the swimlane sees it; this is `EventVisibility`'s default (plan A10) and follows global roles. Replay reads the outbox for five minutes, and a replay follows the visibility rules at the time it is read; a live stream applies the rules of the user it was opened for until it ends (at most 30 minutes), so a change that only narrows what a user may see takes effect when the client reconnects.
- **Outbox delivery is at least once, and a slow commit is not delivered live.** A relay that has not yet read an older row hands it to a stream that subscribed in the meantime, even if that client already has it (an id below the cursor cannot be told from a late commit), so a client may see an event twice after resuming on another replica; the client's refetch is idempotent. A transaction that writes an event and takes longer than the relay's wait for a missing id (10 seconds) to commit is delivered to no live subscriber: its row stays, and only a replay (five minutes) or the next refetch finds it. The prune deletes rows after an hour, so a client that was away longer refetches. The relay's cursor on an outbox emptied by the prune restarts at 0, so the first event after a restart on an idle hub opens up to 4,096 expiring gaps for ten seconds, a bounded and harmless cost.
- **A batch is one statement, one notification per row, and rarely heard out of order.** `publish_many_in_tx` writes up to 200 events with one insert. The `outbox_notify` trigger is `FOR EACH ROW`, so the commit sends one notification per row, 200 at most per batch, where one per transaction would do; that takes a migration, and the relay only treats a notification as a prompt to look, so the cost is a few wake-ups that coalesce. A batch commits atomically and is read in id order, so it is heard in the order it was published in, with one exception that belongs to the relay and not to batching: while the relay works through a backlog of more than its read size (200 rows by default), ids that another transaction drew between the rows of the batch can turn the lower rows into gaps that are read in the next poll, after the higher ones. A single statement draws its ids one after the other, so that needs another session drawing ids at the same instant; events published one at a time in a transaction are far likelier to be apart. An event is a prompt to refetch, so the order within a batch does not decide what a client shows.
- **Delivery to a browser is at most once with a resync.** A subscriber that lags, a listener that reconnects and a replay window that is too old all end in a `Resync`, so a client must refetch; an event can be dropped between the commit and a subscriber's queue. Nothing that matters is kept only in an event, but a client that ignores `Resync` shows a stale screen.
- **An epoch race window of up to 30 seconds.** An agent that moves between replicas is found through `agent_connections`, cached for one second; a replica that dies without clearing its row is believed alive until its `last_seen_at` is 30 seconds old, and requests in that window fail as unavailable or are retried once on a fresh read. No request hangs, but a command may fail that a retry would have delivered.
- **Pull-request events can arrive out of order, and only the last one says where a link is.** GitHub does not order deliveries. A `closed` that overtakes the `reopened` before it leaves a link closed that is open on GitHub, until the next event for that pull request; `opened` is ignored for that reason (a link is created open, and acting on a late `opened` could undo a `closed`), and a merge is terminal whatever follows. The payload's own timestamps are not used. A link that is wrong is repaired by the next event for its pull request, and 06 can re-read a pull request from GitHub with the owning user's token.
- **A sentinel renews by joining again, and the audit action is the agent's.** The `Report` stream has no renewal message, so a sentinel asks for a new certificate with the VM's ID token every day, and each issue is one `agent_joined` audit event with a sentinel actor. `AuditAction` has no sentinel-specific variant (a new variant is a contract change that the plan did not ask for); the actor kind tells them apart in the log. The ID token's validity is the verifier's, as for agents.
- **A refused delta does not stop the stream.** The hub acknowledges what the sink applied and leaves the rest unacknowledged, so the agent resends it, but later messages on the same stream are still handed to the sink. Whether a delta whose predecessor was refused is applied is the sink's decision (05 compares the root a delta is based on with the one it holds and asks for a full scan on a mismatch); the hub does not hold back later messages, and an ack is for one `seq` and never means "everything before".
- **The ID token's validity is the verifier's.** The platform checks the email of the token against the registered service account, and the audience and signature through the `TokenVerifier` port (03a). A flaw in that port is a flaw in `Join`; the 24 hour certificate bounds what it buys.
- **The operations listener is plain HTTP with no authentication.** `/metrics` and `/readyz` are readable by whatever can reach the port; the NetworkPolicy contract limits ingress to the monitoring namespace, and a CNI that does not enforce NetworkPolicy removes that limit. The answers hold no secret, path or id.
- **The pod and network contracts depend on the cluster.** Whether the CNI enforces NetworkPolicy and FQDN policy, whether the image builds and runs as described, and whether base-image digests are refreshed are properties of the environment and of 09; `crates/hub/HARDENING.md` is the contract, and the tests lint the contract, not the cluster.

## Fact engine (04)

Owner: prompt 04. This section covers `crates/engine` as built by tasks T1 to T10: bytes, classes and line endings (T1); parsing, validation and flattening of YAML, JSON and `.properties` (T2); the settings index and locations, which hand the same text to tree-sitter (T3); paths, effective config and tree hashes (T4); drift, diffs and the grid (T5); checks C1 to C8 and effect previews (T6); the secret scan and text search (T7); the batch functions (T8); severity and inline ranges (T9); and the config-server's resolution model with C9 to C11 (T10). The engine is a library: it has no listener, no credential, no clock, no file or network access and no state. It runs inside the hub process, in the caller's `spawn_blocking`, on whatever the caller reads from the registry and the agents. So the questions are: can hostile *content* make it use unbounded time or memory, or crash the hub; can a result carry something that must not leave the hub; and can a wrong *fact* get past the people who rely on it. Who may ask is the caller's guard (S4); what is stored, audited or written is the caller's (05, 06, 07).

A row's Proof cell names tests, benchmarks or fuzz targets that exist in `crates/engine`; `tests/threat_model.rs` fails if one does not, or if a name is a helper and not a test.

### Assets

- **Config content.** File bytes and the settings parsed from them. The files are not meant to hold secrets (D18), but they can (keystores, a pasted token, a password in a value), so every value is treated as one (S13).
- **The hub's availability.** The engine runs on the hub's blocking threads; the nightly full recompute (P6) and a user's compare, grid or text search (P7) all use the same cores.
- **The correctness of facts.** Every view and every MCP answer is built from the engine's output (D33); a wrong drift state, effective hash, grid cell or finding is misleading in the way a wrong number is, and nobody sees it because the screen looks fine.
- **Redaction.** `secret_scan` decides what MCP output and edit warnings hide (S13, S14b). A match holds a line, a column, a length and a rule, never the value.
- **Determinism.** Identical input gives byte-identical output (acceptance 3), so a finding or a hash can be recomputed and compared.

### Trust boundaries

- **Callers to the engine.** The caller (05 for reads and recompute, 06 for edits, 07 for MCP) passes typed values (`NfsPath`, `LogicalFile`, `TenantId`, `TenantSet`, `ChannelName`, `AppName`, `ContentHash`, `Bytes`), never text that nobody has checked (S11). The engine does not authenticate or authorize: it trusts the caller to have done both, and returns facts for whatever it is given.
- **File content to the parsers.** Every byte of a config file is hostile input: it comes from NFS through an agent, from a Git mirror, from a past version, or from an upload that has not yet been confirmed. The Rust parsers read it first, under the limits; only text that they accepted goes on to tree-sitter, a C library (S22).
- **Patterns, globs and rule sets to the matchers.** A search pattern comes from a user or an MCP client; a deny glob, a host rule or a severity rule from an admin. The regex engine is linear-time with size limits (S11); globs are compiled with count and length limits.
- **Property sources to rendered output.** A resource is rendered with values from the property view, and the result is what a service would receive. The view's values are data: they are inserted once and never read as a template, and nothing is read from the process environment.
- **The engine to the log and to the result types.** Error values and `Debug` output carry sizes, names, paths and lines, never content (S21).

### Residual risks

- **tree-sitter is C code reading untrusted bytes inside the hub process.** The Rust parser and the limits stand in front of it, it is cancellable, and the fuzzer runs it under sanitizers, but a memory-safety flaw in the grammar's scanner or in the library would run with the hub's privileges. The mitigation is the pinned version (at least 14 days old, S19), `cargo audit` over both lockfiles, and keeping the C parser on input that is already known to be well-formed.
- **The resolution model is a reconstruction of the config-server's behaviour, and a wrong fact is the main risk (D86).** The property view, the choice of a resource and the substitution of placeholders follow D82 and D83; the points that the docs leave open are recorded as assumptions (plan A6, A10; the order of a channel request's candidates; the search order for resources, which the engine does not decide because a request names its logical file). Until the nightly "as served" differential check (D86, 05 and the agent) runs on real data, a difference would show up as a view that is wrong and looks right. The golden fixtures are reconstructions of the config-server's test data (plan A3), not copies.
- **The batch's effective hash of a property source has three layers.** A tenant file, the base file and the root `application.*` file feed the hash; `application-<tenant>.*` is part of `property_view` (and so of what C10 and render see) but not of the per-file hash in the batch. A change that only touches `application-<tenant>.*` is therefore seen by the property view and not by the tree hash of the file it overrides. 05 should either recompute through `property_view` for property sources or extend `Layers`; the engine does not hide this.
- **The secret scan is heuristic.** It looks for known prefixes, key headers, JWT shapes and long high-entropy strings, never at a key name, a placeholder or a public key. A secret in an unusual shape passes (a false negative), and a long random-looking public identifier blocks a save (Q20: six such files). The thresholds are configuration (`ScanConfig`) and are to be tuned with the Q20 files before 07 goes live.
- **Search hits carry content.** `search_text` returns line text because that is the answer; the engine does not redact it. Every caller that shows a hit to a person or an MCP client must pass it through `secret_scan` (S13, S14b). A caller that forgets is a leak, and the engine cannot see it.
- **Costs are bounded in size, not in time.** A hostile but valid input can still take as long as its limits allow (a 2 MiB file of openers costs about 256 steps per byte in the placeholder scan; a regex at the size limit scans linearly). The limits keep a single call to a bounded, predictable cost, but an attacker who can send many calls is stopped by the callers' rate limits and request limits (S4, 05), not by the engine.

## Write paths and token vault (06)

Owner: prompt 06. This section covers `crates/hub-writes` as built by tasks T1 to T7 and T9 to T11: the write pipeline with its idempotency claims, editing lock, validation and approval step (T1); byte-faithful writes (T2); edit, upload, delete, revert and restart (T3); proposals, approvals, expiry and drafts (T4); the GitHub token vault (T5); the synchronous half of pull requests, which is the reverse mapping, the plan and the Git Data calls (T6); the Teams notifier (T7); pull request links and jobs (T9): the persisted, resumable job that makes a pull request, the one-open-pull-request rule, the approval of a pull request, and the reaction to a pull request that was merged or closed; the reveal action for masked values (T10): the one audited way to see a value the secret scan flags, and the refusal of writes to denied paths at every door; and notify, auto-notify and the restart of the config-server (T11): the one door to the config-server's unauthenticated update endpoint (Q37), the batching of a swimlane's writes into one notification, the pickup states a notification changes, and the restart that check C11 asks for. Sign-in, sessions, CSRF and the audit chain itself are 03a's; the agent's side of a write is 02's; the gateway, the outbox and the leases are 03b's; the registry that observes the result is 05's. This section relies on them and says so where it does.

The module asks two questions. Can someone change a file, a service or a repository without being allowed to, without a record, or against a file that is no longer the one they were shown? And can a user's GitHub token be read by anything but that user's own request? A row's Proof cell names tests, benchmarks or fuzz targets that exist in `crates/hub-writes`; `tests/threat_model.rs` fails if one does not, or if the name is a helper and not a test. A control that is planned but not built has a Proof cell that starts with `None`; the table has none, because what is not built is listed above and in the residual risks.

### Assets

- **The config files on each swimlane's NFS export,** reached only through the agent. A write is a `WriteFile`, `DeleteFile` or `RestartDeployment` command, and the hub never touches NFS itself. The hash the caller expects to find is the precondition of every file command (D44).
- **Content in flight and at rest.** Request bodies (at most 2 MiB of file; the routes allow for JSON escaping), the new version of a proposal (a blob, by hash), a draft (24 hours), and every version a write replaced or created (a blob by hash, D47). Config text is data; it can hold values the scan does not know.
- **Idempotency rows** (`idempotency_keys`). A SHA-256 of the request, never its content, and the stored response. While a write is in flight the row holds its intent: the swimlane, the path, the hashes, and the audit event it will record with a diff in which flagged values are already redacted. Rows live 24 hours.
- **Proposals and approvals.** Who proposed, who decided, and the hash the proposal expects. `lanekeeper_app` can insert an approval and read it, nothing else (migration 0004), and cannot change a proposal's author.
- **The audit events this crate records:** one for each applied write, decision, expiry, token change, restart and notification. They name the actor, and for an approved change the author and the approver (D38).
- **GitHub tokens (S8).** The plaintext exists only inside its owner's request: in the caller's `Secret<String>`, in the cipher's buffer, and in the `Secret` the vault hands to a closure. At rest a row of `github_credentials` holds a fresh AES-256-GCM data key wrapped by Cloud KMS, a nonce and the ciphertext; the associated data is the user id and the credential id. The KMS key's IAM is what stands behind every wrapped key. The linked GitHub login (on the user's row) and the expiry GitHub reports are not secret.
- **Pull request jobs and links** (`pr_jobs`, `pr_links`, T9). A job holds who asked, the paths, the title and the person's text, the state, a failure sentence, and what each step produced: the plan with the *hashes* of its files' blobs (the content is in the blob store, by hash), the branch and commit, the pull request's number and address, and the audit event's id. A link ties a swimlane, a path and an NFS hash to a pull request, and its state (open, merged or closed) comes from GitHub's webhook (03b). Both are bookkeeping that decides whether a second pull request is allowed.
- **The preview key.** The secret `write-preview-key` (at least 32 bytes) from the secret source; with it a preview id is an HMAC-SHA256 token over the user, swimlane, path, action and hashes it was issued for (D46).
- **Flagged values (T10, D79, S14b).** The values the secret scan flags in structured files on NFS. Every view masks them (`[REDACTED: N chars, rule]`); the reveal action is the one path that returns one, to an Editor or above, for a reason, with one audit event. The value exists in the response of the reveal and, briefly, in the memory of the request that reads and parses the file; it is in no table, cache, log, event or error. The audit event keeps the file's hash, the setting, its line and the reason, never the value.
- **The config-server's update endpoint (T11, Q37).** `/update-resources` has no authentication: anything that can reach port 8888 can make every client of a swimlane drop its cache and refresh its context. The hub's only way to it is the `NotifyConfigServer` command to the agent, sent by `ops/notify.rs` and by nothing else; the agent dials its one configured address (02). What the hub protects is who may send the command, with which paths, and that each call is on the record.
- **Pickup states** (`service_state`, `swimlanes.last_notified_at`, T11). What the screens say about whether a service has picked up a change (D85). A notification rewrites them for the services that read the notified paths, in the transaction that records it, so a wrong write here is a wrong fact on every screen and MCP answer that quotes it.
- **The auto-notify queue** (T11). A bounded in-memory queue of written paths, by swimlane and user, between the write path and the batcher. It holds paths and ids, never content, and is lost when the process stops.
- **Teams webhook URLs.** A credential: the query of the URL holds a signature. The settings table names the secret, and the secret source returns the URL.
- **Leases** that serialise a restart of one service and the decision on one proposal across replicas.
- **Events** published through the outbox (`ProposalChanged`, `FileObserved`, `PickupChanged`, `DriftChanged`). They tell the screens to refetch and carry ids, hashes and paths, not content.
- **Availability.** An edit is applied within 1.5 s (P8) and the steady-state queries answer within 50 ms (P12); people lose time, not data, when this slows down, but a restart or an approval that cannot be done is a change that waits.

### Trust boundaries

- **Browser to the write routes.** Every route is registered through `GuardedRouter` with a declared role, behind the platform's limits layer (body cap, JSON depth, timeout, per-IP and per-user rates) and 03a's session and CSRF checks (S3, S4). The body is limited before it is read and read into typed values before the service sees it; the response is a fixed problem that quotes nothing of the request (S11, S21).
- **Browser to the reveal route (T10).** The one route whose success response is a secret. It is guarded like the others (Editor, session, CSRF), takes a small JSON body (16 KiB), and answers `Cache-Control: no-store` whether it succeeds or not. Behind it, the desk asks the directory again for the role, refuses any call that did not come in through the web UI, counts the attempt against the user's window, reads the file through the registry (which withholds a denied file), and commits the audit event before it hands back the value.
- **The service to the user directory.** The `ctx.user` of a request names the user and is trusted for nothing else. The role, the status and the `requires_approval` flag are read from the directory on every action, so a demotion or a disable takes effect on the next call (S4).
- **Hub to agent** (gateway, mutual TLS, 03b). The hub sends the path as a typed `NfsPath` and the expected hash; the agent compares them with the file and refuses on a mismatch, and its own deny globs and cap-std root are 02's. A reply that never arrives is neither a success nor a failure: the write may have run. The hub keeps an intent so that it can find out (the reconcile job), and for a restart it cannot (see the residual risks).
- **Hub to the registry and the blob store.** The registry may be a scan behind, so the file a diff is made against is checked against the expected hash and, failing that, taken from the blob store or the agent. A file the registry withholds (D79) is not read to make a diff. The tool-write registration (05's `ToolWrites`) is made in the transaction that records the write.
- **Hub to Postgres** as `lanekeeper_app`, over verified TLS. The audit log is append-only (01, 03a); approvals are written once and a proposal's author cannot change (migration 0004).
- **Hub to Cloud KMS and Secret Manager.** KMS wraps and unwraps a token's data key under the associated data; Secret Manager supplies the preview key and the Teams URLs. Both are called with a timeout.
- **Hub to `api.github.com` with a user's own token (D41).** HTTPS and TLS 1.3 only, a host allowlist checked at start, no redirect followed, three attempts with full jitter, a cap on the answer, and every answer parsed into a typed value before it is used (S6, S18). The token reaches nothing else.
- **A job to GitHub, later than the request (T9).** A pull request is made by a job after the request that asked for it was answered, and a resumed job may run on another replica. It runs as its author: it opens the author's own token for each GitHub call, after the directory is asked again whether the author is still active and an Editor. Nothing else about the token changes (the same `with_token`, the same host, the same buffers).
- **Hub to the config-server, through the agent (T11, Q37).** The hub sends `NotifyConfigServer` with the paths and nothing else; the agent builds one form value for each path and dials the address it was configured with (02). The endpoint authenticates nobody, so the hub's authorization is the only authorization: Operator, read from the directory on every call, for a person, and an approval for a user who needs one. A status that is not `2xx`, an agent that has no address for the config-server, and an answer that never arrives are three different outcomes, and none of the first two is recorded as a notification.
- **Write path to the auto-notify batcher (T11).** A write that has committed offers its path to a bounded queue; the batcher, a task of the process, makes the calls. The offer never fails or delays the write beyond one indexed read of the swimlane's switch, and runs only after a batcher has been asked for. The batcher is the same code as a person's notify (`notify_as`), so its calls are authorized, claimed, sent and recorded the same way, with `via = system`.
- **Hub to the Teams webhook** (S18). HTTPS, the default port, no user in the URL, a host on the allowlist, no redirect. The card is built from the notification and fixed words only.
- **The engine.** Bytes go in and facts come out, on the blocking pool and at most eight validations at once. The engine's own limits and its residual risks are in its section (04).
- **Container to node and cluster** (S16, S18) and **build to deployment** (S19) are 09's; the crate adds one dependency family, octocrab with hyper-rustls, over the stack's TLS provider.

### Residual risks

- **A landed write that someone else overwrites before the reconcile job looks is not audited as ours.** A write is sent to the agent after the hub keeps its intent (the hashes, the path and the audit event it will record) with the idempotency claim; if the hub then fails before it records the write, the claim stays unfinished. The retry with the same key, or `ReconcileWrites` for a claim older than `stale_claim_after` (60 s), reads the file through the agent and records the write only if the file has the hash that was sent (`resolve` in `reconcile.rs`). If somebody wrote the file in between, the hash differs and the claim is cleared: no audit event is recorded for our write, the intent holds the hash and not the bytes so the version we wrote is not kept, and whether it was ever seen depends on a registry scan having run between the two writes (05, D47). The retry then meets a conflict, not a second write. The window is the time from the landed write to the first look: nothing for a retry after a request that gave up and knew it (it marks its claim, and the retry looks at once), and for a request that died, until its claim is 60 s old and the retry or the next run of the job finds it. The file that is there afterwards is seen by the registry's next scan (05), so its content is not hidden; what is missing is the record of our write.
- **A restart whose answer is lost is not recorded, and a retry restarts again.** `RestartDeployment` cannot be checked afterwards the way a file can: there is no hash to look for. When the command was sent and no usable answer came back (a timeout, a closed stream), `send_and_record` in `ops/restart.rs` releases the claim, writes no audit event and returns `Unavailable`; the Deployment may or may not be rolling. A retry with the same key claims again and restarts again, which is harmless to a Deployment (it rolls to the same template) but means that a restart can happen with no audit event, and that two can happen for one. The hub logs a warning with the swimlane. The same holds for a restart that an admin approves: the proposal stays pending. The only other evidence is outside this crate: whatever the agent (02) logs for the command and the cluster's own audit log.
- **The GitHub token passes through buffers that cannot be zeroized.** `PUT /api/v1/me/github-token` is read by axum as `Bytes` and the handler keeps that body alive for the whole vault call, until it is freed unzeroed; the same bytes pass through hyper's read buffer, rustls's buffers (the hub speaks TLS 1.3 itself, D25) and serde_json's scratch buffer when the text has escapes. The outbound request carries the token in an `Authorization` header that octocrab builds and hyper writes into its write buffer and rustls's record buffer; the header value is marked sensitive but is `Bytes` and is not wiped. What the hub controls is wiped: the caller's `Secret<String>`, the cipher's buffer, the data key and the `Secret` that `with_token` hands out. Reading the rest needs access to the process's memory, which is outside this model (S16, and the same limit as the platform's, 03b).
- **A token save holds a user row lock and a database connection across one KMS call.** `store` in `vault/mod.rs` opens a transaction, locks the user's row with `SELECT ... FOR UPDATE`, reserves the credential row, and only then calls KMS to wrap the data key, because the credential id that the associated data needs is known only once the row exists. It commits after the audit event. The whole transaction is inside `db_timeout` (10 s), and a timeout rolls it back, but until then it holds one pool connection and the user's row, so a slow KMS delays that user's other saves and any other writer of the user's row, and concurrent saves of one user each wait for the lock on a connection of their own. The call needs an Editor, a valid token that GitHub accepts with push access to both repositories, and the user's turn at the per-user rate limit; the audit chain lock is taken after the KMS call, not during it.
- **If a proposal stops being pending between the NFS write and its recording on approval, the write is still audited and the proposal is left as it is.** `follow::apply` locks the proposal's status in the recording transaction, and if it is no longer `pending` (two admins cannot: a lease serialises them; the expiry job cannot while the approval holds its lease, because it takes the same `proposal:{id}` lease for each proposal and skips one whose lease is held, which `the_expiry_job_skips_a_proposal_whose_approval_is_at_the_agent` shows) it logs a warning, records the audit event and the registration anyway because the file changed, and does not write the decision. The admin is told the change was applied; the proposal reads `expired` and has no approval row, and the audit event names the approver, the author and the proposal. What is left is a command that outlasts the 60-second lease: then the job can expire the proposal, and the case below is what happens. `a_proposal_that_expires_while_its_write_is_on_the_way_is_still_audited_and_left_expired` holds the behaviour.
- **A new JSON reader must go through `object`, or serde reads an array as the struct.** serde accepts `["a.yml", ...]` for a struct and `deny_unknown_fields` does not stop it. The readers of T5 were fixed first; the readers of T3 and T4 (edit, revert, restart, draft, approve, reject) had the same flaw and now read through `object` in `routes/wire.rs`, which refuses a body whose first byte after white space is not `{`, with `a_json_array_is_not_an_object_for_any_reader` as the proof. The risk that remains is a reader added later that calls serde directly; `tests/threat_model.rs` fails if `wire.rs` has a second `serde_json::from_slice`. The effect of the flaw was a body the contract does not describe being accepted, never a bypass of a check: every value was still typed and every action authorised.
- **The Teams allowlist may need the tenant's host (Q9).** The default hosts are `*.logic.azure.com`, `*.api.powerplatform.com` and `*.webhook.office.com`. A Workflows webhook whose address is on another host is logged as "not an address that may be called" and the notification is dropped, with no error to the action: the alerts, including audit-chain alerts, never reach Teams until an admin adds the host to `TeamsConfig::allowed_hosts`. The opposite also holds: the three suffixes are shared Azure infrastructure, so the allowlist keeps a card from going to an arbitrary site but not to another Logic App; the URL and the choice of destination are an admin's (a secret name in `notification_settings`), and a card holds names, ids and counts, never file content. Q9 has not named the tenant's host, and the notifier does nothing until a destination is configured.
- **Rejected and conflicting writes leave no audit event.** An action that changes nothing (a conflict, a validation rejection, a lock, a denied path) writes nothing to the chain, as the rule requires; a conflict or a rejection is stored as the answer of its idempotency claim for 24 hours and shows in the logs and the platform's request metrics. Probing for forbidden paths or repeated conflicts is therefore visible in the logs and the RED metrics and not in the tamper-evident trail.
- **One GitHub account can be linked to several users, and no route resets a link yet.** The link is `users.github_login`, and no index makes it unique, so two users who share a token are both allowed; GitHub attributes both pull requests to one account, while the audit event of each names the Lanekeeper user. `reset_github_link` exists as a method (Admin, audited) but has no route (plan A11): an admin cannot unlink through the app until one is added, and a user who changed GitHub accounts is refused until then.
- **The body limits are larger than S11's 4 MiB, and the platform's cap is what binds.** The edit and draft routes allow 12 MiB and 64 KiB of body, because a 2 MiB text can need six bytes a character in JSON; the hub's limits layer (`body_max`, 4 MiB by default) wraps the routes and the smaller limit wins, so an escape-heavy file near 2 MiB is a 413 through the web app. That is the safe direction. When 09 mounts these routes the hub's limit applies; if it raises `body_max`, the memory of one in-flight edit rises with it, bounded by the per-user and per-IP rates and the request timeout.
- **The value-based scan is heuristic, and with the deny globs it is the barrier before content leaves for GitHub.** A secret in a shape the engine does not know (its section lists the limits and Q20) is saved to NFS and committed to the pull request. Both repositories belong to the organisation, and a flagged value is never shown, but nothing stops a secret that the scan does not recognise.
- **A job uses its author's token in the background, after the request that asked for it.** S8 and D42 say a token is used only inside its owner's own authenticated request; a pull request is made by a job (`pr_jobs`) that may run minutes later and on another replica, and the scan resumes one after a crash. This was a deliberate reading of D77 ("PR creation runs as a persisted background job with states"), and **a human DECIDED to allow it on 2026-10-15: D107** (a PR job may use its author's GitHub token at job time; it relaxes S8 and D42 for PR jobs only, and every other use of the token stays inside the owner's own request). D107 is recorded on branch `claude/brave-cori-2cnesi` (commit `564948a`) and lands with main; until main is merged into this branch it is not in this branch's `docs/decisions.md`. The controls that stay, and that the code has: every step asks the directory again for the user (`require_active`, then `authorize` for Editor or above), a token past its expiry is refused, there is one lease per job, tries are bounded (5), a step is limited to 60 s, and the token is never logged, audited or returned. The job opens only its author's credential, so a disabled or demoted author's job fails with no call to GitHub. **The residual risk stays:** the code does not check that a session for the author still exists. A user who has signed out, or whose session was revoked, while still an active Editor, has the job run to the end; demoting or disabling the user is what stops it, and signing out is not. The alternative (the job waits for the person to be present) would stop a pull request from surviving a restart, which D77 asks for.
- **`POST /drafts` takes an `Idempotency-Key` and does not use it, so a retry makes a second draft.** `propose_draft` in `drafts.rs` authorizes the caller and inserts a row; it makes no claim. Honouring the key needs a stored response that is a draft (a new kind beside an outcome and a job), a claim replay for it, and the claim finished in the transaction that inserts the draft; that is a change to the shared idempotency store, left for a human to weigh. The harm is bounded: a draft changes nothing and writes no audit event, a user has at most 100 open drafts (`MAX_OPEN_DRAFTS`), and a draft expires after a day. `a_retried_draft_with_the_same_key_makes_a_second_draft_within_the_open_limit` holds the behaviour.
- **A command that timed out at the hub can still run at the agent, later.** `WriteFile` and `DeleteFile` carry no deadline on the wire (`proto/agent.proto`, a contract), and the gateway's timeout only ends the hub's wait; a command already written to the agent's stream is not taken back. If the agent was slow (a stalled NFS mount is the likely cause), it can run the command after the hub has answered `Unavailable`, after the reconcile job looked at the file and cleared the claim, and so with no audit event. The expected hash bounds it: the agent writes only if the file is still the one the request saw, and the change is then found by the next scan as an NFS change that no hub request made. Fixing it needs a deadline in the command, which is a contract change for a human to approve.
- **A pull request that cannot be recorded is on GitHub with no link.** The job opens the pull request, and only then records its links and its audit event in one transaction. The checks for a second pull request for the same change (the request, the insert under a lock, the plan) leave one gap: two jobs for the same change that reach `opening` at the same moment, where the second `pr_links_one_open` violation fails the job after its pull request is open. The job's sentence names the number and the pull request stays on GitHub with no link and no audit event of ours, for a person to close. A database that is down at that point is not counted as a try, so the scan takes the job up again every 30 s until it answers.
- **Raising a pull request leaves no audit event until it exists.** Accepting a job writes none (it changes only the job's own bookkeeping), and a job that fails writes none; the failure is in `pr_jobs.failure` and the log. Probing for pull requests that fail (a path with a secret in it, a branch that is taken) is visible to an operator in those and in the request metrics, and not in the audit chain.
- **The job's reads can be a scan behind NFS, and a failed approval leaves the proposal `approved`.** The hash a link records is the hash of the bytes the plan read through the registry, which is the pull request's content, and the registry may lag NFS by a scan; the next scan of the file shows the drift. An approved proposal becomes `applied` only when the job has opened the pull request; one whose job fails stays `approved`, and the author raises the pull request again, as a new proposal.
- **`raise_pr` through `WriteService` cannot say why a job failed or give the job to its caller.** `WriteOutcome` has no variant for an accepted job or for a reason, so the trait waits up to 30 s for the job and answers `Applied`, `Rejected` (every failure is `NotAllowed`) or `Unavailable` (the job goes on, and a retry with the same key finds it); the REST route answers 202 with the job and carries the sentence. A user who requires approval gets the proposal outcome from `POST /prs` (200), which the `createPr` operation does not list. Both want a contract change before prompt 07 uses `raise_pr` for the MCP tool.
- **The reveal's limit is kept by each replica, in memory.** `RevealLimiter` is a bounded `moka` table of per-user windows, so with several replicas a user can reveal `reveals_per_minute` times on each in the same minute, and a restart empties it. The limit slows a sweep for secrets and bounds the audit chain's growth; it is not the control that decides whether a reveal is allowed (the role is), and every reveal is recorded wherever it happens. A table of 10,000 users is bounded by eviction, so an attacker with that many accounts could in principle push another user's window out; accounts are Entra's.
- **A reveal needs no approval and no second person.** D79 allows an Editor and above, and a user who `requires_approval` can reveal too, because a reveal changes nothing. The controls are after the fact: the record with the reason, the file's hash, the setting and the line, the rate limit, and the audit chain's review. Someone who is allowed to see a secret can write it down; nothing in the hub prevents that.
- **A reveal is not replayable, so a response that is lost is audited twice.** The route reads the `Idempotency-Key` header as the contract says (a missing or malformed one is a 400) but does not claim it: a stored answer would be the secret. A client that retries after a lost response makes a second reveal and a second event, which is the truth, and both count against the limit.
- **What can be revealed is what the mask hides, and the mask is only as good as the scan.** A secret in a shape the scan does not recognise is not masked anywhere and is not a reveal. A file that cannot be scanned (too many matches, or the scan refuses it) is masked whole, so every setting in it can be revealed, one audited call each. The setting path the person names is recorded only after the file has been shown to hold it.
- **The revealed value passes through buffers that cannot be zeroized.** `Secret` keeps the value out of `Debug`, logs and errors and wipes the copy the desk holds, but the bytes of the file the registry returned, the text the engine parsed and its settings, the serialised body (`serde_json::to_vec`) and what axum and hyper buffer for the response are plain `Bytes` and `String`s, not wiped when freed. The value lives in the process for the length of the request and until the allocator reuses the memory, as the token's buffers do (above).
- **Notify and the config-server restart are built, and stay off the real system until Q37 and Q10 are answered.** `/update-resources` has no authentication (Q37, no default): the chart's NetworkPolicy is off by default, so the hub's Operator rule and the audit trail are the only controls until the config-server's owners allow the agent and nobody else, and approve the call. Q10 (whether ArgoCD, with self-heal on, accepts the `restartedAt` annotation of a restart or rolls it back) has not been tested, and it covers the restart of the config-server as it does any other. Q35 (do services subscribe to change notifications) has no answer either: the hub reads `CONFIG_CLIENT_MONITOR_ACTIVEMQ_ENABLED` from each Deployment (D88) and believes it. Nothing in the code needs the answers; going live does.
- **A notification whose answer is lost is not recorded, and a retry notifies again.** `NotifyConfigServer` is sent with no connection held. When no usable answer comes back (a timeout, a closed stream), `execute` in `ops/notify.rs` releases the claim, records no audit event and returns `Unavailable`: the config-server may have refreshed its clients. A retry with the same key notifies again, which is harmless (a notification refreshes a cache), but the first call stays unaudited, and a lost answer for an automatic notification is logged and not retried at all. The config-server's own log and the agent's are the only record.
- **The config-server's `2xx` is taken at its word, and the pickup states are the engine's reading of it.** The agent passes the status on and does not judge it (02), so a server that answers `200` and does nothing makes services look live. `last_notified_at` is the swimlane's, not a path's, and the engine's `pickup_state` takes one such time for a service: if 05 recomputes from it alone, a change in a folder the notification did not name looks told. This module is stricter (only services that read a notified path are updated), so the two can disagree until 05 reads the services' own state. The hub reads `CONFIG_CLIENT_CACHE_TTL` with its own small parser (seconds, `ms`, `s`, `m`, `h`, `d`, ISO), which 05 may read differently. A service whose waiting changes the hub cannot tell apart (a new folder looks like any other file by its path) is left as it is when it waits for the config-server.
- **A Deployment that declares no `SPRING_APPLICATION_NAME` is assumed to be the application of the folder that has its name.** D88 gives the hub only the environment values the agent reports, so an application whose name is set in its packaged `application.yml` (or anywhere but the Deployment's environment) is not known by that name. Spring Boot's own default is not the Deployment's name, so this is a convention (the folders of the fixtures are named like their Deployments), not a fact. `ops/pickup.rs` applies it in three places: a folder is an application's when a Deployment of the swimlane is called that (`deployment_names`), `<name>.yml` in it is a property source for that Deployment (`undeclared_name`), and the statement that picks the services already matched by name. If a Deployment's real name is another, a notification for its folder is read as a search location for every service, which updates the pickup state of services that did not read the file, and a file named like the Deployment is read as a resource, which can show `live_within_ttl` for a change that needs a restart. The registry's own recomputation (05) may read the same Deployments differently until the two share one definition of an application's name; a human confirms the convention (or the agent reports the name the client uses) before this is relied on.
- **Auto-notify is best effort, and its queue is in memory.** The queue (`auto_notify_queue`, 1,024 paths) is lost when the process stops, a path that finds it full is dropped and counted (`auto_notify_dropped`), a call that fails is logged and not retried, and a replica announces only the writes it handled. The switch (`swimlanes.auto_notify`) is read when a write commits, so turning it on does not announce earlier writes. The person can always press the button, which is why nothing here retries; the cost is a service that waits for a notification nobody sent until someone notices on the pending-restarts screen. A stop of the batcher waits for the calls under way and drops the paths still in its window.
- **The config-server is found by its Deployment name.** The setting config_server_deployment (default `csp-configuration-server`) is matched against the cluster report's Deployments of the swimlane; with none, or with several of that name in several namespaces, no restart is offered, and a swimlane whose config-server has another name offers none until the setting is changed. The affected services are every other service of the swimlane, which over-names them (a service that never asks the config-server is listed) and is cut at 2,000.
- **An approver sees only the first path of a notification, and no action.** `ProposalView` has one `path` and no `action` (the T4 report says so), so a proposal to notify the config-server of ten paths is listed with the first one, a zero content hash and no hunks. The audit event of the approved notification names every path, and the approver is an admin who may read the proposal's row, but the queue does not show what is about to be sent. A change to the view is a contract change.
- **The notify route's answer for an approval user is not in the contract.** `api/openapi.yaml` gives `POST /swimlanes/{id}/notify` one `200` answer, `NotifyResult`, though a user who needs approval gets a proposal (as prompt 06 requires and migration 0004 allows). The route answers that user with the `proposal_created` body every other write route uses; a generated client that validates the `200` against `NotifyResult` alone would reject it. It needs a contract change (a `oneOf` as `WriteResult` has), which this crate may not make.

## Known residual risks (from design)

- **Partly attributed NFS changes.** With the sentinel (D72), edits made on the VM are attributed to a named OS Login user. Writes from NFS clients that happen outside a sync Job are attributed only to "an NFS client", at medium confidence. A root user on the VM could stop auditd; the sentinel's heartbeat gaps are flagged as findings.
- **Cursor's model providers.** Config content sent through Cursor reaches Cursor's model providers. This is accepted because the files contain no secrets (D18), and the six flagged files are pending review (Q20).
- **Delayed lockout.** A user disabled in Entra keeps any active session until it is ended in the app or expires, which takes at most 12 hours. Mitigation: admins can disable the user in the app, which ends their sessions immediately.
