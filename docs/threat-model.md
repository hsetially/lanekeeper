# Threat model (STRIDE)

Each prompt fills in the section for the components it owns, and keeps it current. A human signs off before go-live (S24).

For each component, record:

- **Assets.**
- **Trust boundaries.**
- **STRIDE threats:** Spoofing, Tampering, Repudiation, Information disclosure, Denial of service and Elevation of privilege. Give each threat its mitigation, with the S# it maps to.
- **Residual risks.**

- Agent (02)

- Engine (04)

## Contracts, ports, migrations, fixtures and fuzz skeleton (01)

Owner: prompt 01. This section covers what 01 creates and everything else builds on: the database roles and the audit table protections (`db/migrations/0001_init.sql`, `deploy/dev/init.sql`), the `Secret<T>` type, the typed validators (`NfsPath`, `RepoPath`, `CompareRef`, `GitRef`, `TenantId`, `PathMappingRule`), the proto and OpenAPI contracts, the synthetic fixture generator and the fuzz skeleton. Behaviour behind the ports belongs to the prompts that implement them and is covered in their sections.

### Assets

- The audit chain (`audit_events`, `audit_checkpoints`): the evidence of who changed what (S9).
- Secrets in memory: GitHub tokens, session ids, join tokens, webhook URLs, keys (S7, S8, S21).
- The NFS tree, which only typed paths may address (S11, S17).
- The two database roles, `lanekeeper_migrator` (owns the schema, runs DDL) and `lanekeeper_app` (the hub's runtime identity).
- The contract files themselves, which every other prompt trusts.

### Trust boundaries

- Hub process to PostgreSQL: the hub connects as `lanekeeper_app` and never as the migrator or a superuser.
- Network or API input to the typed validators: the first parse of every path, compare reference, tenant id and swimlane id.
- Agent and sentinel to hub over gRPC: message size limits and the join request shape live in `proto/agent.proto` and `crates/proto`.
- Developer machine and CI to the repository: fixtures are generated, never copied from a real environment.

### Residual risks

- **Owner-level database access.** The migrator owns the tables, so it can disable or drop the audit triggers. Mitigation is outside this prompt: the migrator credential is used only by the migration job, not by the hub, and the signed checkpoints (03a, S9) let a nightly job detect a rewrite. A rewrite after the latest checkpoint, at most one hour, is detectable only by the Cloud Logging copy.
- **Self-approval is guarded on insert only.** The `approvals_no_self_approval` trigger fires `BEFORE INSERT`. `lanekeeper_app` holds SELECT, INSERT, UPDATE and DELETE on `approvals` and `proposals`, so code running as that role (a hub bug or a compromised hub) can insert an approval by another user and then `UPDATE approvals SET approver_oid` to the author, `UPDATE proposals SET author_oid`, or `DELETE` a proposal (the cascade removes its approvals). Mitigation: approval enforcement (S4/D37) is also done in application code in prompt 06. Closing the gap (SELECT and INSERT only on `approvals`, a `BEFORE UPDATE` trigger on `approvals`, an author-immutability trigger on `proposals`) is a possible hardening for prompt 06 or a later contract-change. Accepted by a human at the round 3 review of prompt 01 (reword only).
- **The definer function is a privileged surface.** It is small and bounded. Anything that can call it as `lanekeeper_app` can drop sentinel partitions, but only whole months that ended more than 90 days ago (the floor is fixed in the function), plus default-partition rows older than 90 days; the audit tables are not touched, and deleting a sentinel does not cascade into its records. A caller can therefore make expiry happen when it is due and no earlier. It cannot make records last longer or shorter than the hub's own schedule decides above the floor. Lowering the floor is a migration and a recorded decision, not a runtime setting. Two limits remain: a caller can run the function repeatedly, which takes an advisory lock and briefly locks the parent table (a denial-of-service nuisance, not a data loss), and an owner-level credential is outside this control (see the first bullet).
- **`Secret::expose` is an escape hatch.** The type stops accidental formatting and serialisation, not a caller that reads the plaintext and logs it. Reviewers grep for `expose()`, and the log-capture tests of later prompts cover the paths that matter.
- **Rejection of unusual file names.** `NfsPath` rejects backslashes and control characters, so a real file with such a name cannot be addressed. This is deliberate (plan Q13); it surfaces as a finding rather than a silent skip.
- **A base file whose name ends in a known tenant id** is reported as a tenant file (plan Q14). This is a limit of the naming scheme, documented in `mapping.rs`.
- **Fuzzing coverage is a skeleton.** Three targets run 30 seconds each per smoke run. Parsers added by later prompts (YAML, `.properties`, Markdown chunking, webhook payloads, proto decoding at the hub) must add their own targets (S22).
- **The development database passwords** in `deploy/dev/init.sql` are for local use only; production roles come from CloudNativePG managed roles (09).

## Agent (02)

Owner: prompt 02. This section covers `crates/agent` as built by tasks T1 to T11: configuration and the cap-std root, joining the hub and renewing the certificate, the gRPC transport, the Merkle tree and scans, the durable spool, quiescence and sync tagging, deny globs, file operations, the Kubernetes watchers and restarts, operations (health, metrics, logs), and the pod contract (`crates/agent/Dockerfile`, `HARDENING.md`, `RBAC.md`). The hub's side of the same links (issuing certificates, authorising commands, auditing) is 03a and 03b; the NFS VM sentinel is 17. The config-server calls (T12) are not built yet: "Not built yet" below says what they will add.

The agent reports facts and carries out commands. It decides nothing: the hub checks the user's role, writes the audit event and sends the command. So this section asks two questions of the agent: can an outsider use it, and can a command from the hub do more than its shape allows?

### Assets

- **The client private key and certificate** (ECDSA P-256; the certificate lives 24 hours). They prove which swimlane the agent is (S5). The key is made in memory and stored only in the certificate Secret.
- **Join credentials:** the Google ID token for the agent's service account, and the one-time join token of the fallback (single use, valid 24 hours). Either one gets a certificate.
- **The NFS export of one swimlane** (`LK_NFS_ROOT`): the files the config-server serves. Integrity matters most, because a wrong byte is served to a bank's services. The files hold no secrets by design (D18), but keystores and keys may sit among them (D79).
- **The stream to the hub**, which carries file reads, writes, deletes and restarts.
- **The spool volume** (`LK_SPOOL_DIR`, a small persistent volume of its own, outside the NFS export): a copy of every version the scanner saw and the hub has not yet acknowledged, up to 512 MiB or 100,000 entries. It holds file content at rest, so it is as sensitive as the export. Integrity matters too: a version in it is sent to the hub as if the agent had just seen it.
- **The agent's Kubernetes access:** its service-account token, the Roles in `RBAC.md` (get, list and watch on Deployments, Pods and Jobs, and patch on Deployments, in the configured namespaces; get and update on the certificate Secret and get on the join-token Secret, both by name).
- **Cluster facts the agent reports:** Deployment and pod names, labels, environment variable names, and the values of the names on the hub's allowlist (D88).
- **Logs and metrics:** paths, hashes and ids, which must stay free of contents and secrets (S10).
- **Availability and freshness:** the agent's tree is how the hub learns of an out-of-band change within 15 seconds (P1).

### Trust boundaries

- **Agent to hub** (gRPC over TLS 1.3, one pinned CA, mutual TLS on the stream, no client certificate on `Join`). The hub is trusted to authorise commands. The agent still checks the shape of everything it receives, and clamps the settings the hub sends.
- **Agent to the spool volume.** Written and read only by the agent. What it reads back after a crash is untrusted: a cut or damaged file, or one that someone with access to the volume changed. Each record is checked (length, checksum, metadata) and then decoded and validated like a message from anywhere before it is sent.
- **Agent to the NFS export.** The export is written by others too: the config-server's jobs, the dataload Job, people on the VM. Everything under the root is untrusted input: names, symlinks, sizes, special files.
- **Agent to the Kubernetes API server** (service-account token, namespaced Roles). Responses are untrusted text and are trimmed on ingest.
- **Agent to the node's metadata server** (`169.254.169.254`, plain HTTP, node-local), for the ID token.
- **Agent to the config-server pods** (port 8888, plain HTTP, no authentication, Q37). The NetworkPolicy contract reserves this destination; the calls themselves are T12 and do not exist yet.
- **Container to node and cluster:** non-root, read-only root file system, no capabilities, RuntimeDefault seccomp, no shell, egress limited to five destinations (`HARDENING.md`).
- **Kubelet and Prometheus to the health port** (`9090`, plain HTTP, no authentication, three read-only paths).
- **Build to deployment:** the image is built from `crates/agent/Dockerfile` on digest-pinned bases with `--locked`; crates are exact pins (S19).
- **Chart and operator to the agent:** the environment variables are trusted configuration, validated at start.

### Residual risks

- **A deny glob decides by name, not by content (D79).** `*.pem` finds a key called `server.pem` and does not find one called `id_rsa`, `credentials` or `app.yml`, nor a password inside an ordinary config file. The built-in list is the one D79 names; the hub can add globs, and the secret scan on the hub (S14b) is the second line for values inside files. The agent cannot tell a key from its bytes without reading them, which is what the list exists to avoid.
- **Bytes that were spooled before a path became denied stay on the spool volume.** When the hub adds a glob, the pump strips the bytes from every record it replays, so they never reach the connection; but a record already written to a segment file keeps them until the hub has acknowledged it and the segment is deleted (mode `0600`, on the agent's own volume). The same holds for the hub: what it received before it sent the glob it still has, and marking a file denied does not change the Merkle root (the root commits to content, not to policy), so the hub is not told again about a file that does not change. Rewriting the spool on a change of globs would close the first part; it is not built.
- **The hash of a denied file is sent (D79).** The name, the size and the SHA-256 of the content go to the hub, because the hub must see that the file exists and that it changed. A hash lets whoever holds it check a guess of the content offline; for a random key that is no help, for a short password in a file it is. A `DENIED` answer carries no hash, so the hash is not available by commanding a write or a delete either.
- **Before the hub's first configuration only the built-in globs are in force.** A glob the hub adds applies from the moment its configuration is read (before the spool is replayed, and before the next command), and a walk is started at once to re-mark the tree; files the hub's own globs deny, and the built-in globs do not, are not denied in the first moments of a start. The built-ins are never absent.
- **A hub can deny files it should not.** A glob such as `*` makes every file denied: the agent then reports names, sizes and hashes only and refuses all commands on files. That is the hub choosing to see less, and it is bounded (1,000 globs of at most 512 bytes), but it is a way for a compromised hub to make the agent useless.
- **The spool is file content at rest.** Anyone who can read the spool volume (cluster administrators, the node) reads recent config, as they can read the export. Encryption at rest is a property of the volume, not of the agent, and the files are not encrypted by it. A file that no deny glob matches, whatever it holds, is in the spool too.
- **A damaged region costs the rest of its segment.** Records are framed without a resynchronisation marker, so a bad byte in the middle of a segment loses the records after it in that segment (up to 4 MiB) and not just the one it is in. The loss is reported, and the hub's root comparison recovers the state; the intermediate versions are gone.
- **A version can be sent twice.** Delivery is at least once: after a crash, the acknowledgements of the last second may not have been written down, and a delta whose acknowledgement was in flight is sent again with the same sequence number. The hub applies a delta by hashes, so a repeat changes nothing, but a hub that records an event per delta must deduplicate by sequence number.
- **A full or failing volume loses versions, not the agent.** If the volume is smaller than `LK_SPOOL_MAX_BYTES`, or fails, an append fails (`ENOSPC`, I/O error): the delta is not spooled, the segment is abandoned, and the hub learns of the change through the heartbeat root and a `RequestDelta`. The chart must size the volume above the byte bound. Appends sit in the path of P1, so a slow volume delays every delta by its fsync.
- **A hostile writer can push history out.** Someone who can churn files on the export fills the spool faster than the hub can drain it during an outage, and the oldest whole deltas go first. The gap says so; the last state is never lost, because the tree and the heartbeat root are not in the spool.
- **A gap waits for a delta to ride on.** The loss is stamped on the next delta sent. With an empty spool and nothing changing, it waits; the hub sees the root mismatch meanwhile and asks for a full scan.
- **The hub is trusted to authorise.** A compromised hub, or an agent certificate stolen within its 24 hours, can read any regular file of at most 2 MiB under the root, write or delete one against its current hash, and restart any Deployment in the configured namespaces. The agent bounds what a command can be (typed paths, hash, size, namespace) but does not decide whether a command is wanted. The agent has no revocation list; ending a stolen identity is the hub's job (03b).
- **Key and token material cannot be wiped everywhere.** The agent wipes its own copies, but the key's bytes pass through hyper, kube, rcgen and TLS library buffers that it cannot zeroize. The Kubernetes client deserialises whole Deployments, environment values of variables that are not allowlisted included, before they are trimmed away; those strings are dropped, not wiped. The certificate Secret holds the private key in the cluster: anyone who can `get` that Secret (cluster administrators) or read the node's memory or disk can take it, and encryption at rest is a property of the cluster.
- **A join token cannot be renewed (token-only clusters).** The fallback token is single-use. If the agent loses its stream and cannot renew over it before the 24-hour certificate runs out, the re-join has no valid token, and the agent stays disconnected (`/readyz` fails) until an Admin issues a new one. Clusters with Workload Identity re-join on their own. This follows from Q26.
- **A renewed certificate reconnects the stream.** The session reconnects when the outbox is empty, or after 30 seconds at most. A command that is running at that moment gets no reply, and the hub times it out.
- **`verify` does not check the chain's signature.** `ClientIdentity::verify` checks the key, the SAN, the lifetime and the parse. The signature is checked by the TLS handshake (the hub checks our certificate against its CA on every stream), not at join.
- **NFS has no compare-and-swap.** Between the hash check and the rename, another writer on the export can change the file, and a replace or a delete then overwrites that change. The window is one rename. Creates are protected (hard link). The sentinel (17) is what shows who else wrote.
- **A file swapped for a FIFO can block a thread.** If a regular file is replaced by a FIFO between the `lstat` and the `open` (the walker and file operations both have that window), the `open` blocks until something opens the other end. The caller of a file operation gets `IO` after 30 seconds, but the blocked thread, and the lock stripe it holds, stay stuck until then; the walker's thread would stall the scan until `/healthz` fails after 11 minutes and the kubelet restarts the container. Sixteen blocking threads exist. This needs write access to the export and good timing; there is no `O_NONBLOCK` guard. This was found by reading the code and is not covered by a test.
- **Leftovers and hidden names.** A crash between staging and renaming leaves a `.lanekeeper-tmp-*` file that nothing sweeps. The walker ignores names that start with `.lanekeeper-tmp-` or `.nfs`, so anyone with write access can hide a file from the hub by using such a name. New files are mode 0644 and owned by the agent's uid; whether the config-server can read them depends on `root_squash` and the uid (Q11, 1010 by Q4), which must be settled before the agent writes on a pilot swimlane.
- **Symbolic links are invisible to the hub's commands.** A link is never followed, even inside the root, so a config file that is a link is reported as an entry the hub can neither read nor write. This is deliberate (S17).
- **A write racing a long scan.** A tool write that races a scan longer than 2 seconds may push one extra delta. It is harmless: the next walk finds the file unchanged.
- **The service-account token is mounted.** The agent needs the Kubernetes API, so anything running in the container can read the token. There is no shell and no second process, but a Role cannot limit `patch` to one annotation: a stolen token could patch the image or command of any Deployment in the configured namespaces.
- **The Kubernetes link is the client library's.** It uses rustls with aws-lc-rs and verifies the cluster CA, but the kube client also accepts TLS 1.2; only the hub link is forced to 1.3 (S6). A watcher whose list keeps failing retries with backoff for ever, logging only the HTTP status; the cluster report then stays "not synced".
- **Plain-HTTP hops.** The metadata server (node-local) and the config-server (T12, Q37, no authentication) are reached without TLS. The NetworkPolicy contract limits who can be reached; it does not make the hop private.
- **The log filter cannot prove a negative.** The Kubernetes client crates are silenced and other libraries are held at `warn`, but nothing proves that no other library ever logs text that the hub or the cluster chose. The agent's own logs hold file paths, which an NFS writer chooses; JSON escaping keeps them to one line.
- **The pod contract depends on the cluster.** The image build has not run (no Docker daemon where this was written), a NetworkPolicy is ignored by a CNI that does not enforce it, the metadata address and port are placeholders until a real node confirms them (Q26), the hub and API-server CIDRs are values the chart fills in (Q1), and the health port is unauthenticated. Base-image digest pins receive no fixes until someone changes them, and there is no signature or SBOM check on the image (09).
- **A hung NFS mount is noticed late.** File operations time out after 30 seconds, but `/healthz` fails only after the scanner has made no progress for 11 minutes.
- **A stale cluster delta after a reconnect.** A delta that was blocked in the 8-slot report channel while the hub was away can be sent after the full report that follows the reconnect, and then stays stale until the next change or the next report request.

- **Anyone who can create a Job in a watched namespace can open a sync window.** A Job whose name matches `LK_SYNC_JOB_NAME_GLOBS` (default `*dataload*`) or carries the configured label opens a window; changes seen while it runs are tagged with it, and the hub holds drift alerts until it closes (D75). A Job that never finishes would keep them held. The agent does not bound the length of a window: the hub (05) must, and must show a tag from a window that is older than the Job's normal run as such. Namespace write access is already trusted with the export's content (the dataload Job writes it).
- **Quiet is estimated from file times.** The quiet period counts from the newer of a changed file's mtime and ctime, read from the NFS server and compared with the agent's clock; a skew of seconds makes a batch go out early (more deltas, never a lost change) or up to that much later (P1 has about 2 s of headroom beyond the worst case). A removal has no time and counts from the walk that saw it.
- **A change hidden by attribute caching is tagged late or not at all.** If the NFS client caches attributes, a walk can miss a file written during a window until the cache expires or the 15-minute full rehash finds it; the window's close may then already have been sent, and the delta arrives untagged. The hub sees it as out-of-band drift (a false alert, not a missed one).
- **Window events are not acknowledged.** A close lost with a connection is repeated on the next one, for an hour; a hub that was away longer does not learn of it, and a window it holds open must be bounded by the hub.

- **Config-server calls (T12, Q37).** `NotifyConfigServer` and `FetchServed` to an endpoint with no authentication. Every call must come from a hub command that the hub has audited and restricted to the Operator role; the agent must never call it on its own. `FetchServed` returns file content from the config-server, so it must follow the same deny list as every other path to a file (D79): a denied name is answered `DENIED`, and the config-server's response is not returned for it.

## Known residual risks (from design)

- **Partly attributed NFS changes.** With the sentinel (D72), edits made on the VM are attributed to a named OS Login user. Writes from NFS clients that happen outside a sync Job are attributed only to "an NFS client", at medium confidence. A root user on the VM could stop auditd; the sentinel's heartbeat gaps are flagged as findings.
- **Cursor's model providers.** Config content sent through Cursor reaches Cursor's model providers. This is accepted because the files contain no secrets (D18), and the six flagged files are pending review (Q20).
- **Delayed lockout.** A user disabled in Entra keeps any active session until it is ended in the app or expires, which takes at most 12 hours. Mitigation: admins can disable the user in the app, which ends their sessions immediately.
