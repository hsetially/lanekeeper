## Design in brief

`crates/hub-writes` is a library. It holds the `WriteHub` (the `WriteService` implementation), its Postgres stores (idempotency, proposals, drafts, PR jobs, credentials), the vault, the GitHub client wrapper, the Teams notifier, the leased jobs, and the REST handlers as a `mount` function for `hub_platform::GuardedRouter`. The hub binary is not edited by this plan (A15).

**The write pipeline** (T1) is a fixed sequence of steps. Each step is a small function so the order is visible and testable:

1. `authorize`: `Users::require_active(id, min)` (one indexed read; the `ctx.user` snapshot is never trusted for the role), floor Editor for file actions, PRs, drafts and token routes, Operator for restart and notify.
2. `claim`: insert the `idempotency_keys` row for `(user, key)` with the request hash (SHA-256 over an action tag and length-prefixed fields, never the content itself). Same key and same hash: replay the stored response, or wait at most 3 s for the first request to finish and then answer `Unavailable`. Same key and another hash: `IdempotencyConflict` (422). Rows live 24 hours.
3. `lock`: the swimlane's `editing_unlocked` flag; `Locked` (423) when false. File actions only.
4. `validate`: engine `validate` and `secret_scan` inside `spawn_blocking`. Parse errors block; duplicate keys are warnings; a secret match blocks and reports line numbers and rule ids, never text.
5. `approval`: for `requires_approval` users, insert a proposal (72 h), write one audit event, publish `ProposalChanged`, notify admins; the response is `ProposalCreated`.
6. `execute`: tx 1 is only the claim. The agent call (`WriteFile`, `DeleteFile`, `RestartDeployment`, `NotifyConfigServer`) runs with no connection held. Tx 2 stores the blob, completes the tool-write registration, records exactly one audit event, publishes events through `publish_in_tx`, and stores the response on the idempotency row, all in one transaction. Rejections, conflicts and locks change nothing and write no audit event.

**Crash window (A1).** A write can land on NFS and the process die before tx 2. The claim row stays unfinished (`response_status IS NULL`) and carries a small intent (action, swimlane, path, expected, new hash) in `response_body` while it runs. A retry with the same key, or the leased `ReconcileWrites` job for claims older than 60 s, asks the agent for the file: if the current hash equals the intended new hash the write is completed in tx 2, otherwise the claim is failed and cleared. This needs no migration.

**Reads the pipeline needs** come from `RegistryRead::content` (current bytes, class, EOL, encoding, BOM), the shared tables read by plain SQL for the lock flag, deployed tenants, path mappings and merge modes, and the engine. Nothing is parsed twice: the validated parse is reused for the stored diff and the effect preview.

**Modules** (all under `crates/hub-writes/src`): `lib.rs`, `error.rs`, `clock.rs`, `config.rs`, `service.rs` (`WriteHub`), `pipeline/{mod,authorize,claim,lock,validate,approval,execute}.rs`, `idempotency.rs`, `fidelity.rs` (T2), `ops/{edit,upload,delete,revert,restart,notify}.rs`, `preview.rs`, `proposals/{mod,store,approve,expire}.rs`, `drafts.rs`, `vault/{mod,crypto,store,lifecycle}.rs`, `github/{mod,client,api,types}.rs`, `prs/{mod,target,plan,job,runner,links}.rs`, `teams/{mod,cards,webhook,breaker}.rs`, `reveal.rs`, `autonotify.rs`, `routes/{mod,files,upload,proposals,prs,me,notify,reveal}.rs`, `reconcile.rs`, `testing.rs` (behind a feature, for the hub's route-table check).

## Tests, benchmarks and fuzz targets

- **Unit and property.** `fidelity` (proptest: for any text, any file style, `prepare_content` keeps the target's EOL, BOM and encoding and changes only the lines the caller changed), request-hash canonicalisation (proptest: field boundaries cannot collide), preview token (proptest: any bit flip fails), card building, breaker state machine, PR path planning.
- **Integration against real Postgres 16** (testcontainers, or `LK_TEST_PG_ADMIN_URL`; migrated as `lanekeeper_migrator`, used as `lanekeeper_app`). Gateway, notifier, KMS envelope, secret source, blob store and registry read are the `ports` fakes.
- **Conformance.** `ports::conformance::write` runs against `WriteHub` with a `WriteScenario` adapter over the fake agent.
- **Golden.** The Adaptive Card JSON per notification kind (insta), the audit event for each action (insta, so the canonical form is pinned), the problem bodies for 409, 422 and 423 (no internal detail).
- **Mocked externals.** `tests/support/fake_github.rs`: a local HTTP server for `GET /user`, repository permission checks, blobs, trees, commits, refs and pulls, with rate-limit headers, delays and failures. `tests/support/fake_teams.rs`: a local webhook server with scripted failures.
- **Fuzz** (own crate `crates/hub-writes/fuzz/`, the 02, 03a, 03b and 04 pattern, because `fuzz/` at the root is closed to extra targets): `writes_request_json` (arbitrary bytes as each request DTO), `writes_upload_multipart` (arbitrary multipart bodies), `writes_preview_id` (arbitrary strings as a preview id), `writes_github_token` (arbitrary strings through the token-shape check), `writes_github_responses` (arbitrary bytes through every GitHub response parser). - **Benchmarks** (criterion, registered in `perf/budgets.toml`, run by `hub-writes-bench` with a filtered registry as `identity-bench` does): `edit_applied` (budget `P8`: the whole `edit` call, Postgres container, fake agent that answers like the real one, a 2,000-file swimlane's worth of other rows present, 100 edits round-robin over files of 1 KB to 150 KB including the 6,000-line file) and `write_queries` (new budget `P12.hub_writes_queries`, 50 ms p95: the claim, lock read, open-PR lookup, proposal list and expiry scan, credential load, at target-scale row counts). Both are loopback numbers; prompt 16 measures staging.

## Risks

**Security**

- **Unaudited landed write (A1).** The commit that carries the audit event comes after the NFS write. Contained by the same-key retry, the leased reconcile job, an alert counter on unfinished claims older than 60 s, and the threat model entry. Still a gap of a few minutes in the worst case.
- **Token vault.** The plaintext token lives only inside `with_token`, in `Secret<String>`, and is zeroized on drop; the data key is zeroized after wrap; associated data is user id plus credential id; no token in any `Debug`, error, log field, audit event or response, proved by a log-capture test over every path. The GitHub client must not put the `Authorization` header into error text.
- **Self-approval is enforced in application code** (the insert trigger does not stop a later UPDATE by a caller holding the grant). G10 closes it in the database; if refused, it is a recorded residual risk.
- **Reveal and the secret scan.** The reveal route returns a secret by design: Editor and above, rate-limited, no-store, always audited, never logged. The scan is heuristic (engine residual risk); a false negative saves a secret.
- **Auto-notify and the unauthenticated `/update-resources` (Q37).** Only the agent's `NotifyConfigServer` path is used; every call is audited; A13 keeps the Operator rule.
- **Preview tokens.** HMAC key from Secret Manager, constant-time verify, ten-minute life, bound to user, path, action and hashes; replay inside the window is harmless because the expected-hash check still applies.
- **New dependencies.** At most octocrab (A9); each is pinned at least 14 days old, justified in the PR, and checked by `cargo deny` and `cargo audit`. AES-256-GCM and HMAC come from `aws-lc-rs`, already in the graph.

**Performance**

- **P8 on a real network.** The benchmark is on loopback with a fake agent, so it bounds hub code and database time only. The design keeps the hub-side work to two short transactions plus one blocking parse, with the blob write and the audit append in tx 2. The multi-replica case adds one internal gRPC hop (03b), modelled by a delay in the test; prompt 16 measures staging. If either misses, work stops with the measurements.
- **Audit contention.** Each write takes the audit chain lock once (3 ms budget, P12). Auto-notify batching and PR jobs add events; they do not hold the lock across a network call.
- **2 MiB to 3 MiB files** cost one blocking parse and one secret scan each (`P6.parse_flatten` budget 20 ms); both run in `spawn_blocking`, and never inside a transaction.
- **Unbounded things avoided.** Every queue, cache and batch has a size (the auto-notify batcher, the throttle tables, the moka caches, PR job counts, 100 paths per request); every outbound call has a timeout and bounded jittered retries.
