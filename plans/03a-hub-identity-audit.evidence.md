### B2 (blocking, rule 5): the verifier read every column with no bound. Real; fixed.

Only `event_json` had a size `CHECK`. The `jsonb` columns, the unindexed text columns, the hash columns once the domain check is dropped, and the checkpoint columns had none, and sqlx buffers a value whole before `serde_json` decodes it. The reviewer's figure (about 18 bytes of peak memory per byte of text, 507 MB for 28 MB of text, a `jsonb` ceiling of 256 MB, two decoded per row) is the reason: one row ends every run out of memory, with no alert.

- *Fix: bound in the query.* `columns::select_list()` selects each bounded column as `CASE WHEN octet_length(col) <= N THEN col END AS col` (for `jsonb`, `octet_length(col::text)`) and adds `oversize`, a bitmask of the columns that were left out. An oversize value is never sent, buffered or decoded; the column is reported as differing, like any value no event can have written. The chain's `prev_hash`, `hash` and `event_json` and the checkpoint columns are bounded the same way (`chain_batch_sql`, `checkpoint_batch_sql`): an oversize value comes back `NULL`, which is already "a row the chain cannot vouch for" and "a checkpoint that cannot be checked".
- *The bounds, derived from the one the log enforces* (`log::MAX_EVENT_JSON_BYTES`, 1 MiB, checked by `prepare` before the lock and by the table's `CHECK`): a copy is a part of one event, so a text column is bounded by 1 MiB (`TEXT_COLUMN_LIMIT`). `jsonb` prints a space after every `,` and `:`, each next to an element of at least one byte, so its text is at most 1.5 times the compact form; the bound is twice the event (`JSONB_TEXT_LIMIT`, with a compile-time assertion that it is at least 1.5 times, and `the_text_form_of_a_jsonb_is_at_most_one_and_a_half_times_its_compact_form` measuring the worst case on the server). A hash is 32 bytes. For the checkpoint: a signature 128 bytes (`checkpoint::MAX_SIGNATURE_BYTES`, the job's own limit), a key version 512 (`KeyRef::MAX_LEN`), an object name 43 (the prefix, a `u64` and `.json`, tested against `object_name(u64::MAX)`). In practice every legitimate value is far below these. No legitimate event can exceed them: `what_the_log_writes_for_a_largest_event_is_under_every_bound` (unit) and `the_largest_event_the_log_accepts_verifies_clean` (integration: every `ShortText` at 256 bytes of multi-byte text, a path of about 950 bytes, a 64 KiB diff, three events, a checkpoint, a nightly run: `Clean`).

(3) Table test: 14 new "oversize" cases (one for every compared column except the two of fixed size, `at` and `approval_id`: 2 MiB of text, a `jsonb` of over twice the megabyte, 33 bytes of hash), each reported as that column alone; `the_tamper_cases_cover_every_compared_column_changed_and_removed` requires them (they passed against the scaffolding, since an unbounded read also reports a column that differs: the transfer tests are the red ones). (4) `an_event_json_over_the_limit_is_a_hash_failure_even_when_its_hash_is_consistent` (the size `CHECK` dropped and the hash recomputed over the long text, so that size is the only thing wrong: `ChainHashMismatch` at that row; against the old code the row passed and the damage showed a row later as a broken link) and `a_hash_column_of_the_wrong_size_in_the_chain_is_a_hash_failure_not_an_error`.

So the memory held is a chunk, not the batch. The worst legitimate row is about 72 KiB (the diff is at most 64 KiB, `AuditEvent::MAX_DIFF_BYTES`, and every other field is a few hundred bytes), so about 230 of them fill a chunk, and 5,000 of them are about 360 MB in the table but never in memory at once. ### B1 (blocking, S9): the new bound for the `jsonb` columns could itself fail the query. Real; fixed.

**Reproduced first** ([S], PostgreSQL 16.15, `psql`, one probe at a time with a statement timeout): a `jsonb` number is stored as a compact `numeric` and printed in full. 100 numbers of `1e131000` are 1,620 bytes stored and print as 13,100,303 bytes. 9,000 of them are 144,020 bytes decompressed and 2,483 stored in a table (the table compressed them with `pglz`), and printing them fails: `ERROR: 54000: out of memory ... Cannot enlarge string buffer containing 1073700589 bytes by 131001 more bytes` (1.6 s here, 22 s on the reviewer's machine). 7,000 are 112,020 bytes decompressed and 1,944 stored, and print as 917,021,003 bytes in 7.9 s here (13 s on the reviewer's machine), every time they are printed. `1e-16383` prints 16,387 bytes (100 of them 1,638,703 bytes), and a zero with the largest scale (`0e-16383`) the same, though it is an integer; `5.` followed by 16,000 zeros prints 16,000 bytes. A `jsonb` nested 16,000 deep is accepted on input (it takes 17,000) but `jsonpath` fails on it with `stack depth limit exceeded` between 10,000 and 11,000 levels (a hard error, which the `silent` argument does not suppress). 100 MB of one byte compresses to 1,144,705 bytes with `pglz` (87:1) and to 392,179 with `lz4` (255:1). The reviewer's reading of the cause is right and the account in this file, the PR text and the threat model of this as a limit that needed a value of hundreds of megabytes and an owner was wrong: the INSERT-only role writes both columns freely, and about 2.5 KB stored is enough. **The record of that claim is removed** from the threat model, the PR text and this file.

**The design.** The select never prints a `jsonb` it has not vetted, and it evaluates nothing that can fail or grow on the value before the value is known to be small. One searched `CASE` per column (a searched `CASE` evaluates its conditions in order and stops at the first that holds, which `AND` does not promise), the conditions in this order and each at most once per row, the JSON `null` literal for a value that is not vetted, the value last:

1. `pg_column_size(col) > 8192`: the stored size, from the header; nothing is fetched from the TOAST table and nothing is decompressed for a value stored large;
2. `pg_column_size(col #> '{}') > 8192`: the size once decompressed (the path `'{}'` hands the detoasted value back). A value stored under 8 KiB decompresses to at most about 2 MB (`lz4`, 255:1), so this is bounded work, and the raw size bounds the nesting depth (8 bytes a level at least, so 1,024) far under the depth where `jsonpath` fails, and the number of numbers;
3. `jsonb_path_exists(col, 'strict $.** ? (@.type() == "number" && (@ > 9223372036854775807 || @ < -9223372036854775808 || @ != @.floor()))', '{}', true)`: a number past the range of an `i64`, or not an integer, found by value without printing it (`1e131000`, `-1e131000`, `1e-16383`);
4. `jsonb_array_length(jsonb_path_query_array(col, 'strict $.** ? (@.type() == "number")', '{}', true)) > 16`: an integer can still carry a scale (`0e-16383` prints 16 KB), which value cannot show, so what a value may print is bounded by how many numbers it has;
5. only now `octet_length(col::text) > 16384`. After 1 to 4 the value has at most 16 numbers of at most 16 KB each and a raw size under 8 KiB (strings print at most six times their size), so this prints at most a few hundred kilobytes, cannot fail, and is the bound on what is sent.

A value that is not vetted is replaced by the JSON `null` literal. No event holds that in these columns (an absent value is SQL `NULL`; `Field::of` treats a JSON `null` in the event as absent, so a JSON `null` in a column is never the copy of anything), so it is reported as that column differing, and `read_row` also records it as unreadable. That replaces the second flag of round 3 and with it a second evaluation of the same checks: **each expensive expression is evaluated once per row.** The limits are derived from the types and not from the size of an event: the two columns hold an `Actor` or an `Evidence`, whose text fields are `ShortText` (256 bytes) and whose one number is a time in milliseconds; the largest is about 700 bytes, `JSONB_COLUMN_LIMIT` (8 KiB) is more than ten times that, `JSONB_TEXT_LIMIT` is twice it, `JSONB_NUMBER_LIMIT` is 16 (a legitimate value holds one), and `the_jsonb_bound_is_more_than_ten_times_the_largest_value_the_types_allow` fails if the types grow to a tenth of the limit. Derived from the event (1 MiB), as round 3 had it, the cost of a poisoned row would have been tens of milliseconds a row and a batch of them a timeout.

**The same class, everywhere else.** Every cast and render in the verifier's SQL was listed: `octet_length` of a `text`, `bytea` or domain over `bytea` reads the length from the header (it neither detoasts nor copies, so it cannot fail), and it is what the text, hash, `event_json` and checkpoint columns use; `approval_id` and `seq` are selected as they are (8 bytes); `at` is cast only under `CASE WHEN isfinite(at)`, whose epoch in microseconds is at most 20 digits; the mask is a sum of small constants; the checkpoint query, the two probes and the `SET LOCAL` text contain no cast at all. `nothing_the_verifier_selects_is_cast_or_rendered_except_what_is_vetted_first` keeps that list: it parses every `::` in every SQL text the verifier sends, fails on any type outside `jsonb` (the sentinel), `text`, `numeric(40,0)` (the time), `int4` (the mask), pins how many of each there are, asserts the checkpoint query and the probes have none, and asserts that each `::text` of a `jsonb` follows the four checks in its column's `CASE`.

**Tests, through the INSERT-only app pool** (the role that can write these values; `append_copy_with` copies the head row, chains it correctly and sets one column): for the 9,000-number value, the 7,000-number value, 9,000 of `-1e131000`, of `1e-16383` and of `0e-16383`, 300 of `0e-16383`, 8 of `1e131000`, a number past the largest `i64`, a value nested 16,000 deep (where `jsonpath` fails) and one 1,100 deep, in `attribution_evidence`, and four of them in `attribution_actor`: one poisoned row at 13, three legitimate events after it (14 to 16), a tamper of the stored event at 15 by the owner, then `nightly().run_once()`: the outcome is `Failed` (never `Errored`), the failures are exactly `[ColumnsDiffer({that column}) at 13, ChainHashMismatch at 15]`, `events_checked` is 15, the errors counter is 0, one alert, and the run took under 5 s (they take well under one). `several_poisoned_rows_do_not_add_up_to_a_timeout`: ten rows of the 7,000-number value in both columns, three legitimate events, a tamper at 25: `Failed` in under 10 s with 11 failures. `a_jsonb_the_select_does_not_vet_is_sent_as_the_json_null_and_a_vetted_one_as_it_is` runs the batch query itself against each value and asserts what comes back (the JSON `null` for each poison, the value unchanged for what the log writes, both extremes of an `i64` and `5.0`, SQL `NULL` still `None`, no row over 32 KiB). `each_check_on_a_jsonb_rejects_what_it_is_for_and_lets_the_rest_through` evaluates each of the five checks by itself on 19 values stored in a table (so that the stored size is the real one), a check only where the ones before it let the value through (as the select does: `jsonpath` itself refuses the 16,000-deep value). `the_largest_attribution_of_every_kind_of_actor_verifies_clean_and_is_far_under_the_bound`: the largest `OsLogin` and `Job` actor with the largest evidence and the earliest time, three events and a checkpoint: `Clean`, and the decompressed size of each column times ten is under the limit. Measured in the sandbox ([S], `psql`): the five checks over 22 hostile values, two of them 20 MB and 30 MB decompressed, took 39.5 ms in all.

**Cost.** [S], `psql`, `EXPLAIN (ANALYZE, TIMING OFF)`, 5,000 rows with a realistic actor and evidence (100 bytes stored), only the two `jsonb` columns, five runs each: reading them plain 0.7 to 1.2 ms; round 3's guard (printing each twice) 4.5 to 7.5 ms; round 4's vetting 19 to 31 ms (median about 23 ms). ### N1: a position used twice. Real; fixed.

The reviewer's scenario (a row moved onto the position of the one before it, the chain intact in the order the rows come back) is the first test below, and it failed against the old keyset read on its outcome. The cause is the keyset read, `seq > last`, which skips the second of two rows at the position that ends a batch; inside a batch nothing compared a row's position with the one before. Now: the walk carries the last position compared (`ChainState.last_seq`) across chunks and batches, and a row whose position is not after it is `FailureKind::EventPositionDuplicated` (checkpoints: `CheckpointPositionDuplicated`), once per position. A batch starts **at** the last position the one before it read (`seq >= $1`), reads the rows that share it again, first, and skips as many as the one before compared (`Cursor`, `BatchSeen`), so that all the rows of a position are in one batch whichever side of the edge they were on and none is compared twice. If a whole batch is rows at one position, `>=` would ask for the same rows again: the position is reported and the next batch starts after it (`Resume::After`), so a position held by more rows than a batch (5,000) is compared only as far as a batch reaches into it, and the chain then does not link after it (documented in the module docs and the threat model; tested with batches of 2 and 3 against a position held by 3 rows, which must end and report it). A `(seq, hash)` keyset was considered and not used: it needs the `(seq, hash)` index to order the read, a row with a `NULL` hash is skipped by a tuple comparison, and the order of rows that share a `seq` still would not be promised. `ChainVerifier::with_batch_rows` now takes at least 2 (a batch of one row cannot show a repeat); `with_checkpoint_batch_rows` is new (default 500) so the checkpoint edge can be tested with a small batch as well as with 600 rows. The checkpoint's event is now **looked up** (`LEFT JOIN LATERAL ... ORDER BY (e.hash = c.head_hash) DESC NULLS LAST LIMIT 1`) and not joined: found by the test below, a join made two rows of one checkpoint when two events share its position, and the verifier reported a checkpoint twice that exists once. Tests: `two_events_at_one_position_are_a_finding_even_when_the_chain_is_whole` (the reviewer's scenario: exactly `[EventPositionDuplicated at 9]`, 12 events, 2 checkpoints, one alert naming position 9), `a_repeated_position_is_found_wherever_it_falls_against_the_edge_of_a_batch` (five repeats, at the start, in the middle and at the end, against batches of 0, 1, 2, 3, 4, 5, 6, 7, 12, 13 and 5,000 rows: exactly one finding each, 12 events, with a 30 s bound so that a loop fails and does not hang), `several_rows_at_one_position_are_found_and_the_walk_goes_on_when_the_batch_holds_them`, `two_checkpoints_at_one_position_are_a_finding`, `two_checkpoints_at_one_position_are_found_across_the_edge_of_a_batch` (600 checkpoint rows, a copy of the 500th, so that the copy is the first row of the second batch), `a_repeated_position_where_a_checkpoint_is_does_not_repeat_the_checkpoint`. To say which of two rows at one position comes first, these tests drop the primary key, put an ordinary index on `seq`, and read through a pool whose connections may neither sort nor scan (`enable_sort` and `enable_seqscan` off): the rows then come back in the order they are stored, an `UPDATE` stores its copy after the old rows, and "an event moved up" leaves the chain whole. `nightly_verify_streams_in_bounded_batches` now expects 2 batches for a log that fills one exactly (the second finds the last row alone, skips it and is short). `the_verifier_reads_the_chain_by_the_primary_key_without_sorting` still passes on the new query (`seq >= $1 ORDER BY seq LIMIT $2` is an index scan on the primary key).

### N5 (the human's "option 1"): an alert after N unfinished nights in a row. Done; the count is in memory.

`NightlyVerifyJob` counts the nights in a row that ended without a verdict (`Errored` and `Incomplete`; `DEFAULT_ALERT_AFTER_FAILED_RUNS` = 2, `with_alert_after`; 0 and 1 are the same: every unfinished night alerts) and from the Nth tells the admins through the notifier that carries every other alert: title "Audit log verification is not completing", summary "Audit log verification could not complete 2 nights in a row (last error: the audit tables did not answer in time)." (the number of nights and the class of the last error, or the SQLSTATE of a refused shape, never the text of an error), every night until a run completes. `Clean` and `Failed` (a run that ran to the end) reset it. `NotLeader` (this replica did not run) and `LeaseLost` (the run was abandoned because the lease was lost) **neither count nor reset**: another replica decides that night, and nothing was learned about the database; decided and documented, with a test for each. A refused shape also alerts at once through the findings path and is counted as an unfinished night (so the second night sends both the finding and the count). Prometheus: the new gauge `audit_verify_unfinished_runs_in_a_row` (`CounterSource::gauges`, a default method, so nothing else implementing the trait changes) and the existing `audit_verify_errors_total`, which rises on every unfinished run; the alert expressions are listed in `metrics.rs` (`increase(audit_verify_errors_total[3d]) >= 2` and `increase(audit_verify_runs_total[36h]) == 0` read history that survives a restart).

**Persistence: option 2, and its cost.** The `Leases` port is `try_acquire(name, ttl) -> LeaseGuard` with no payload or holder metadata, and every other table the app role can write belongs to another prompt and has no free slot (`outbox` is published to the event stream, `feature_flags` belongs to docsearch); using any of them would be a hack. `db/migrations/` is a contract path, so no table was added. The count therefore lives in the job: **a restart of the pod, or the lease passing to another replica, resets it.** A pod that restarts every day and fails every night never reaches two; two replicas that take the lease on alternate nights never do either. Recommended for a human: approve a contract-change PR that adds `audit_verify_state (id boolean PRIMARY KEY DEFAULT true CHECK (id), unfinished_runs integer NOT NULL, last_error text, updated_at timestamptz NOT NULL)` with one row, `GRANT SELECT, INSERT, UPDATE ... TO lanekeeper_app`, written by the verifier after each run; the job would read it under the lease. Until then the Prometheus expressions above are the way to alert without the limit. Stated in the module docs, the threat model, this file and the PR text. Tests (`mod nights` in `audit_verify.rs`, a lease that every night's run gets, and a lock held by the owner so that a run gives up after 200 ms): `the_second_unfinished_night_in_a_row_alerts_and_the_first_does_not` (also: every night after, the exact text, then a clean run ends it), `a_clean_run_resets_the_count`, `a_failed_run_resets_the_count_too`, `an_incomplete_run_counts_as_an_unfinished_night`, `a_changed_shape_alerts_on_the_first_night_without_waiting_for_a_second`, `a_run_that_lost_its_lease_neither_counts_nor_resets` (the gauge stays 1: not 2, not 0), `a_replica_that_did_not_hold_the_lease_neither_counts_nor_resets`, `the_number_of_nights_is_configurable_and_never_below_one`, `a_notifier_that_is_down_does_not_stop_the_count_or_the_run`, and `a_renewal_period_of_zero_is_a_millisecond_and_not_a_panic` (the test knob that lets a run lose its lease quickly is clamped, because `tokio::time::interval` panics on zero).

**Design choices the reviewer raised in round 1 and that were deliberately not implemented** (for the human; the reviewer's reasoning, not mine):

15. **The verifier does not enumerate the bucket.** It checks a bucket object only for a checkpoint row that exists. An owner who truncates the tail of `audit_events` and deletes the matching `audit_checkpoints` rows gets a clean run, although the bucket still holds the objects. Cheap fix: a bounded prefix `list` on `CheckpointBucket`, so the objects without a row are found. Now written in the threat model's residual risks.
16. **Random session cookies each cost one indexed read.** A client can send any number of random session cookies and each is looked up. Option: a bounded negative cache, or a WAF or ingress rate-limit note for prompt 09. Not done.
18. **Rows the shipper cannot read are never sent to Cloud Logging** (`audit/shipper.rs`, near line 175). The shipper logs an error with the position, moves its cursor past the row and ships nothing for it, so the copy can lack an event.
19. **The nightly verification is not incremental, and its time at one million events is unmeasured.** It rereads the whole chain every night; with round 1 it also parses each event and reads 16 more columns per row. Item 5 still stands.
20. **One foreign malformed cookie hides all cookies** (`session/cookie.rs`, near line 88): the `Cookie` header parser refuses the whole header when any cookie in it is malformed, so one malformed cookie from another application on the same host name keeps the session cookie from being read at all.
21. **The first-sign-in notification is awaited inline, for up to 5 s**, after the transaction has committed. It delays the redirect, not the commit.
22. **`just verify` skips the Postgres-backed tests when Docker is missing** (it prints `SKIPPED` unless `LK_REQUIRE_DOCKER=1`), so a green `just verify` without Docker says little about them. `verify-03a` sets the variable.
