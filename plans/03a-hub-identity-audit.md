## Design notes

These are the decisions that shape the tests. Anything that needs a human is also in the ambiguity table.

**Token crate (decision B1, needs a human).** The prompt names `openidconnect`. Its 4.0.1 release depends unconditionally on `rsa ^0.9.2`, which has the open advisory RUSTSEC-2023-0071 (Marvin attack, `patched = []`, still affected as of 2026-09-12). `cargo audit` in `just verify` (S19) would fail, and the crate brings RustCrypto `rsa`, `p256`, `p384` and `ed25519-dalek` as a second crypto stack next to the stack's one provider (aws-lc-rs). Proposed: do not use `openidconnect`. Use `jsonwebtoken` with its `aws_lc_rs` backend for signature checks and write the authorisation-code flow ourselves (discovery, authorise URL, PKCE S256, form-encoded token exchange, id-token checks); every check the prompt lists stays in our code and has a named test. Fallback if refused: `openidconnect` plus a recorded advisory ignore in `deny.toml` and `.cargo/audit.toml` (two more Extra-paths) with the argument that the flaw concerns private-key operations and we only verify. I will confirm both facts with `cargo audit` and `cargo tree` at the start of T1 and stop if they differ.

**HTTP to Entra and Google (decision B2).** Outbound calls (discovery, JWKS, token endpoint, Google certs, GCS, the metadata server) go through one `HttpsClient` trait. The production implementation is hyper's HTTP/1 client over `tokio-rustls` (TLS 1.3 only, aws-lc-rs, system roots from `rustls-native-certs` because `webpki-roots` is refused by `deny.toml`), not `reqwest` (second TLS stack). Every call has a 5 s timeout, a 1 MiB response cap and at most 2 retries with jitter, and the host must be on an allowlist built from the config (`login.microsoftonline.com`, `www.googleapis.com`, `storage.googleapis.com`), so a poisoned discovery document cannot redirect the hub to another host. Tests inject `FakeHttps`; one test runs the real client against a local rustls server with an rcgen certificate to prove the TLS 1.3 only rule, the timeout and the body cap.

**Login state (decision B3).** `/auth/login` seals `{state, nonce, pkce_verifier, return_to, exp}` with AES-256-GCM (aws-lc-rs, random 96-bit nonce, `__Host-lk_login` as associated data) into a 10-minute cookie. The key comes from `SecretSource` (name in config), so any replica can finish a login another replica began, with no new table. `return_to` must match `^/[^/\\]` and is re-validated at the callback (open-redirect test). Single use: Entra rejects a reused authorisation code, the cookie is cleared by the callback, and the id token's nonce must equal the cookie's nonce, so a token from an earlier login fails. There is no server-side one-time record, which is residual risk R3 in the threat model.

**Sessions.** The session id is 256 random bits from aws-lc-rs, base64url in the cookie; only its SHA-256 is stored (`sessions.session_hash`). The CSRF token is a second random value; the cookie `__Host-lk_csrf` (not HttpOnly) carries it, the request header `X-CSRF-Token` must equal it, and its hash must equal `sessions.csrf_hash`, so a cookie planted from a sibling subdomain does not pass. Sign-in always creates a new session and deletes any session the browser presented (fixation). A role or status change deletes every session of the user in the same transaction as the change and the audit event, then publishes `UserSessionsRevoked` in that transaction (outbox, fanned out after commit). Idle time is checked against `last_seen_at`, which is written in batches (at most once a minute per session) off the request path, so the idle limit is accurate to about two minutes across replicas; this is stated in the threat model. A pending or disabled user can hold a session, but every guarded route answers 403 with a problem type that says which (D36); `/auth/callback` redirects such a user to a web page that explains it (prompt 08).

**Cache and fail-closed behaviour.** Cache entries hold the session row and the user's role and status for at most 30 s. A subscriber task per replica evicts on `UserSessionsRevoked`, flushes everything on `Resync`, and, if the event stream ends, switches the cache off (every request reads the database) until it resubscribes. Cache misses are single-flight per session hash so a cold start does not stampede the database. The cache never stores the CSRF token, only its hash.

**Authorization is declared.** Routes can only be added through `GuardedRouter`, whose `route` methods take the required role as a parameter; the role gate, CSRF layer and auth layer are applied by it, not by the caller. `RequireRole<R>` and `ActiveUser` read the `AuthContext` that the layer inserted and check again (defence in depth). A mismatch between the registered role and an extractor's role can only make a route stricter. There is no attribute macro: a proc-macro crate would be a new crate outside this prompt's paths (decision B4). `assert_default_deny` closes the gap that a function-based registry has: it calls every registered path without a cookie on the real router and fails unless the answer is 401 (or the route is declared public), and the fallback handler is guarded as well, so a route added around the helper still hits default-deny for unauthenticated callers.

**The audit chain.** `record` runs, in the caller's transaction: size check on `diff` (before taking the lock), `pg_advisory_xact_lock(<constant key>)`, `SELECT hash FROM audit_events ORDER BY seq DESC LIMIT 1` (the genesis hash when empty), `ports::canonical_json` and `ports::chain_hash`, `INSERT` with the denormalised columns from the event. The hash functions are the ports' single definition, so the database `CHECK (hash = sha256(prev_hash || event_json))`, the nightly verifier and the fakes agree. The lock is held until the caller commits, so every audited transaction is serialised from `record` to commit: callers must call `record` as the last statement before commit, and the rustdoc and the threat model say so. Rolled-back transactions leave `seq` gaps (the sequence is not transactional), so the verifier follows `prev_hash` links and never assumes contiguous `seq`. A `UNIQUE(prev_hash)` constraint already stops a fork if the lock were bypassed; a test proves that too.

**Checkpoints.** Message to sign: `lk-audit-checkpoint-v1 || seq (u64 be) || head hash`, digest = SHA-256 of that, signed by `KmsSigner` with the configured `KeyRef` (ECDSA P-256 asymmetric key). The object `audit/checkpoints/<seq>.json` (`{seq, head, signature, key_version, created_at}`) is created with `ifGenerationMatch=0` in the locked bucket, then the row is inserted into `audit_checkpoints`; if the object exists already with the same bytes the job treats that as done (restart safety). The public key is configuration (the SPKI of the KMS key version), not a secret. If there is no new event since the last checkpoint, the job skips.

**Nightly verification.** A leased job streams the chain in batches (keyset on `seq`, never the whole table in memory), checks every link and hash against the stored `event_json`, then for every checkpoint checks that the chain hash at `seq` equals `head_hash`, that the bucket object exists and equals the row, and that the signature verifies with the public key. Any failure raises an alert through the `Notifier` (`CriticalFinding`, severity critical), increments `audit_verify_failures_total`, and logs the seq and the reason (never the event content).

**Cloud Logging copy (decision B8).** `record` cannot know when its caller commits, and a log line written before commit could describe an event that rolls back. So a leased `AuditLogShipper` reads committed events by `seq`, one log line each (`audit_event_hash`, `seq`, action, actor, swimlane, path, hashes, via, request id; `diff` is left out and replaced by `diff_sha256` and `diff_len`, because S10 says logs hold hashes and not content). On start it resumes from the last checkpoint's `seq`, so a restart repeats at most an hour of lines; the hash is the log entry's dedupe key. The copy is at-least-once and lags by the poll interval (5 s).

## Risks

**Security.**

- **The id-token and bearer-token verifiers are the highest-impact code.** A mistake (accepting `alg=none`, trusting `kid` from the token to pick a URL, skipping `tid`) is an account takeover. Contained by: an algorithm allowlist of RS256, no URL taken from a token, the many negative tests in the traceability table, the `identity_jwt` fuzz target, and a mock provider that can mint every bad shape.
- **Dependency choice (B1).** `openidconnect` would put an unpatched advisory and a second crypto stack in the graph. The plan avoids it; the cost is writing the flow ourselves, which the tests are shaped to check.
- **Session revocation must reach every replica (S2).** Contained by the outbox event, `Resync` flush, cache-off when the stream ends, and a 30 s ceiling; `disabled_user_cut_off_on_other_replica_within_1s` proves the normal path. Residual: a replica partitioned from Postgres serves cached sessions for up to 30 s.
- **Login state in a sealed cookie (B3).** A shared key means a leaked key allows forged login cookies (still no session without a valid Entra code and id token). The key is in Secret Manager, never logged, and a test proves redaction.
- **Audit integrity.** The app role cannot update or delete; the nightly job and the locked bucket catch a database owner who disables the trigger. A database owner who also controls the signing key path could forge a chain; the KMS key's own IAM is the control (prompt 09). Truncating the tail between two checkpoints is detected only up to the last checkpoint (at most an hour of history), which is stated as residual risk.
- **Secrets and logs (S10, S21).** Cookies, tokens, client secrets and assertions are `Secret<T>` or hashed at once; the log-capture and Debug-redaction tests fail if any appears.

**Performance.**

- **The advisory lock serialises every audited transaction** from `record` to commit. At design scale (writes are human-paced, tens per minute) this is fine, but a caller that does slow work after `record` would hold the lock. Contained by the rule "record last", the contended benchmark, and the stop-and-escalate condition.
- **Auth overhead (2 ms).** Warm path is one moka lookup, a SHA-256 and a constant-time compare, well under budget. The cold path has one indexed read; it is single-flight and measured separately (`P7.auth_middleware_cold`). A database under load is the risk, which P12's EXPLAIN tests watch.
- **Last-seen writes** are batched and bounded, so they cannot become a write per request; the cost is idle-timeout precision of about two minutes.
- **Nightly verification and the log shipper** stream by keyset in bounded batches under leases, so a large chain cannot exhaust memory or run on three replicas at once; the nightly run has no budget of its own in `docs/performance.md`, so I will report its measured time at one million events in the PR.
- **Benchmarks run on loopback.** They prove code and query cost, not network latency; prompt 16 must confirm at staging.
