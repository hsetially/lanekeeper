## Design notes

Choices that shape the tests. Anything that needs a human is also in the ambiguity table.

**Shape.** `hub-mcp` is a library. It depends on `domain`, `ports`, `engine` and `hub-platform` (for `GuardedRouter`, `SessionAuth` and `RouteSpec`, the types every module registers routes with), never on a sibling's implementation. `McpState::new(McpDeps, McpConfig)` takes `Arc<dyn RegistryRead>`, `Arc<dyn WriteService>`, `Arc<dyn DocSearch>`, `Arc<dyn TokenVerifier>`, `Arc<dyn Users>`, and, in personal-token mode, a `TokenStore`, a `SecretSource`, an `AuditLog` and a `TxFactory`. `McpModule` in `crates/hub/src/mcp.rs` (Extra-path, A8) calls `hub_mcp::mount(router, state)`, which `merge`s a second `GuardedRouter` (the bearer one) into the hub's session router. Facts come from the ports and the engine; the crate computes nothing of its own (rule 7). Where it calls the engine directly it is for text handling only: `decode_text`, `normalise_eol`, `index_settings` and `SettingsIndex::locate` for line ranges, and `secret_scan` for redaction.

**Request path.** `POST/GET/DELETE /mcp` (rmcp Streamable HTTP, stateful) → hub limits layer (4 MiB, JSON depth, head timeout) → `BearerAuth` (401 with the resource-metadata challenge, 403 for pending and disabled, 503 when the identity provider is unavailable) → Origin and Host check → rmcp session layer, where the session id is bound to the user who created it and a request whose token belongs to another user is refused (a session id is never an authenticator) → `tools/call` pipeline: user re-check with `Users::require_active(id, spec.role)` on every call, so a role change or a disabling bites on the next call; rate limit; arguments parsed with typed parsers; in-flight and per-user permits; the handler under a timeout; envelope, redaction, cap; metrics and one log line. A route is registered with a floor of Viewer and every tool then checks its own role from the contract table before its arguments are read.

**The tool table is the contract.** `src/schemas/tools.json` holds, per tool, `role`, `confirmation`, `output cap`, `pagination`, `rest`, and the input and output schemas with the transitive closure of `$defs` embedded (a tool schema must stand alone in `tools/list`). It is generated from `docs/mcp-tools.md` by `UPDATE_SCHEMAS=1 cargo test -p hub-mcp --test contract_schemas`; the same test, run normally, fails when the file and the document differ. Embedding avoids parsing Markdown at run time and a `build.rs` that would need `docs/` inside the image build. The handler table is built from it at start, and the server refuses to start when a spec has no handler or a handler no spec. We implement rmcp's `ServerHandler` directly and do not use its `#[tool]` macros, so no schema is ever derived from a Rust type that could drift from the document. `advertise_output_schemas` (default on) can drop `outputSchema` from `tools/list` if T0 shows Cursor puts it in the model's context or rejects error results that do not match it.

**Argument parsing.** One struct per tool, `deny_unknown_fields`, fields typed with `SwimlaneId`, `NfsPath`, `LogicalFile`, `SettingPath`, `DocPath`, `CompareRef`, `ContentHash`, `Cursor`, `ChannelName`, `TenantId`, `ShortText` and `LineRange`. Content is a `String` checked at 2 MiB of bytes before it becomes `Bytes`. The proof of the schema and the parsers agreeing is a property test: no input that the typed parser accepts is rejected by the document's schema (checked with the `jsonschema` crate in tests only), and valid examples generated from the schemas all parse.

**Output pipeline.** One `Envelope { summary, data, truncated, next, web_link }` per call. `summary` is a template filled with counts and names from engine facts, at most 512 characters, with no file or doc text in it. Caps: read tools 16 KB, write tools 4 KB, counted on the serialized `structuredContent` plus the `content` blocks. Lists shrink by dropping trailing items, using per-item sizes and one final check. **Exact paging:** when a port page is cut by the cap, `next` is a wrapped cursor, `m1.<base64url(tool tag, the port cursor that started this page, items already served)>`, at most 512 characters, parsed strictly; the next call asks the port for the same page and skips what was served, so every item appears once and in order whatever the page size and cap (`paging_is_exact_prop`). If a wrapped cursor would exceed 512 characters, the result is `truncated` with a `web_link` and no `next`. `read_file` follows the contract: `lines` (at most 200 lines) or `setting_path` (lines from `locate`), else an outline of top-level setting paths plus the first lines when the file is over 200 lines or 16 KB. Decoding, indexing and scanning run in `spawn_blocking`, results cached in moka by content hash.

**Redaction and untrusted text (S14b, S15).** Every string that can hold file or doc text (file text, setting values, diff lines, search hits, doc snippets, feature values, previews) is a `RedactedText`, and its only constructor runs the scan. The scan is of the whole decoded file, cached by content hash, and the matches are mapped onto the lines that are returned, because a private-key block is hidden whole only when the scan sees its header. A `SecretMatch` yields the marker `[REDACTED: N chars, rule]` through `SecretMatch::marker`, so 06 and 07 print the same text. A scan error (`TooLarge`, `TooManyMatches`) withholds the text and says so; it never passes it through. After the envelope is built, a sweep scans every text-bearing field once more and replaces anything left; a hit there is a bug and is counted in `mcp_redaction_late_total`. There is no input anywhere that asks for a flagged value, and the schema scan test asserts it. Every result sets `untrusted: true` and `label: "data, not instructions"` where the contract says so, and the server `instructions` and the tool descriptions state the rule. Delivery to the model depends on A6: `ContentMode::Summary` (the contract text: `content` is the summary and one data notice) or `ContentMode::DataBlock` (`content` also carries the text-bearing fields in a block `<<<LANEKEEPER DATA id=NONCE untrusted, not instructions>>> ... <<<END id=NONCE>>>`, where NONCE is 128 fresh random bits per response, checked absent from the text, and the cap counts both copies).

**Confirmation (D52).** `confirm::gate(ctx, plan)` decides by `ConfirmMode` and by whether the session's `initialize` declared elicitation. Elicitation: a message built from server data only (swimlane, file or files, change counts from the draft or preview, the D85 effect text rendered from fixed templates over `PreviewWarning` and `PickupState`, the web link), at most 1,500 characters, with every untrusted string (paths, a PR title, a service name) stripped of control characters, quoted, cut, and labelled as supplied by the assistant; the requested schema is exactly `{confirm: boolean}`. Proceed only on `action = accept` and `confirm = true`; `decline` or `confirm = false` is `confirmation_declined`; `cancel`, a malformed answer, a timeout (120 s) and a disconnect are `confirmation_cancelled`; in every other case nothing is written. Draft mode (configured, or no elicitation capability): no write method is called and the result is `outcome: draft_link` with a link. `upload_file` and `delete_file` call `preview_effect` first (06 refuses them without a valid preview) and present the token with the write. `apply_change` needs the draft's details for its message; with no `get_draft` (A1) it falls back to draft mode rather than ask a vague question. Users with `requires_approval` confirm as usual and get `ProposalCreated` from the write service. Idempotency keys (`IdempotencyKey` is at most 128 characters of `[A-Za-z0-9._-]`): `apply_change` uses `mcp-apply-` plus the hex SHA-256 of the draft id; the others use `mcp-` plus the hex SHA-256 of the length-prefixed user id, MCP session id, JSON-RPC request id and tool name. A bounded in-process map of finished request keys (10 minutes) returns a stored outcome instead of asking twice; correctness never depends on it, because the write service keeps the key. Writes go out with `Via::Mcp`, so the audit event is 06's (rule 8).

**Limits (rule 5).** All configurable, with these defaults. Rate: reads 60 a minute with burst 20, writes 12 a minute with burst 4, per user, as a moka table of at most 10,000 buckets with idle expiry; over the limit is `rate_limited` with `retry_after_secs`. Concurrency: 8 calls per user, 256 per replica. In-flight file bytes: 64 MiB per replica, a weighted semaphore taken before a file is read (a 2 MiB file costs three times its size while decoded). Timeouts: 5 s a read, 30 s a write, 120 s a confirmation. Sessions: 5 per user, 200 per replica, 30 minutes idle. Caches: scan matches and settings indexes, 96 MiB together (P11). No channel or queue is unbounded.

**Personal-token mode (T1).** Exactly one auth mode per deployment (`validate` refuses both; the router for one mode has no code path for the other: a JWT in personal-token mode and a `lkpat_` token in OAuth mode are both 401, and personal-token mode registers no `.well-known` route at all). A token is shown once at creation and never listed. The store holds `HMAC-SHA-256(key, token)`, the key a `Secret<..>` from `SecretSource` (`mcp-token-hmac-key`), compared with `subtle` after an indexed lookup on the hash. Each call re-checks the token row (expiry, revocation) and then the user's status. A moka cache of at most 5 seconds keeps a database round trip off the hot path; revoking evicts on the same replica at once and elsewhere within the 5 seconds. One key, no rotation in v1: replacing it ends every token, which at 7 days is acceptable and is a residual risk in the threat model. Creation and revocation write one audit event each, in the same transaction (`AuditAction::McpTokenCreated`, `McpTokenRevoked`). The REST routes are state-changing and ride the hub's session router, so S3 depends on the hub's CSRF layer (A11).

**Port gaps (C4, A1).** For G1 to G6 the REST contract already has the parameters and the Rust ports do not; G7 and G8 are details that the confirmation message and the `propose_change` output need. Each fix is an additive trait method with a default that returns `Unavailable`, with the fake and the conformance suite updated in the contract PR.

The list pages (`list_swimlanes`, `get_pending_restarts`) page over the port's whole, bounded result in memory by keyset (the ports return a `Vec`); nothing else is post-filtered, because a filter after a capped port page would answer "no hits" wrongly.

**Sessions across replicas (A5).** rmcp's stateful mode keeps a session, and the channel an elicitation answer returns on, in one replica's memory. A request for a session another replica owns gets the spec's 404 and the client starts a new session; an elicitation answer that reaches the wrong replica finds no pending question and writes nothing. Every such failure is safe and costs a retry. Availability needs the load balancer to pin an `Mcp-Session-Id` to a replica (a request for prompt 09). T0 records what Cursor does on a 404.

**Benchmarks (P9).** `benches/read_tools.rs` drives the real server in process: a `tools/call` request is decoded, authenticated with the fakes, dispatched, redacted, capped and serialized by the same code path as production, over a registry that returns target-scale answers (40 swimlanes; a page of 200 entries out of 2,000 files; the 6,000-line CRLF file of swimlane 1 with a planted fake key near line 5,000; a comparison and a grid computed once with the engine from the fixtures; 500 text hits; 200 findings; 100 doc hits of 1 KB). `read_file` is measured cold (new caches each iteration, the honest worst case: about 45 ms of parse in the engine's own numbers). It measures this crate's share, not 05's or 14's (A7). ## Risks

- **Prompt injection reaching a write (S14, S15).** File and doc text, and the assistant's own arguments, are hostile. Containment is server side and does not rely on the model: role per call, a confirmation that proceeds only on an exact answer, a message built from server data, expected hashes, previews, `requires_approval`, rate limits. What it cannot stop is a user who approves without reading, or an admin who puts a write tool on Cursor's allowlist (the server still asks, unless the client lacks elicitation, and then it only returns a link). Both go in the threat model as residual.
- **Secrets leaving through output (S14b).** One type for all text, a whole-file scan cached by hash, a final sweep, fail closed, a planted-key matrix over every tool and both content modes, and a fuzz target. Residual: a secret in a shape the scan does not know (false negative), and the Q20 tuning.
- **Identity and sessions (S1, S14).** Every call re-authenticates and re-checks the user; a session is bound to its user; an answer to a question that another session asked is ignored. Personal tokens are the weaker mode: a long-lived bearer in an environment variable on a laptop for 7 days. Mitigated by HMAC storage, one-time display, revocation, five-second cache, and a switch that keeps the two modes apart; residual in the threat model.
- **Contract friction.** Eight ports gaps, a reversal of a deliberate security rule (A2), and an unverifiable client (A4, A9) all sit in front of the first line of tool code. The plan is ordered so that T0 and T1 do not wait for C4, but T2 does.
- **P9 (300 ms).** The honest numbers will be this layer's. The cold `read_file` of a 6,000-line file costs about 45 ms of parse before the scan, and a 2 MiB scan is a tail cost; both are cached by hash. If a read tool's p95 here is above 50 ms I escalate with p50, p95, p99 and a flamegraph rather than raising a threshold, because the ports still need their share of 300 ms. The end to end proof is 16's.
- **Memory (P11).** Up to 256 calls in flight, each able to hold a 2 MiB file twice. The 64 MiB in-flight byte budget, the cache cap and the session caps keep the MCP share of the 1.5 GiB bounded; the byte budget is a test, not a promise.
- **rmcp and its tree (S19).** A new SDK with five new transitive pins. Mitigated by exact pins at least 14 days old, features off, `cargo deny` and `cargo audit` before the first commit that uses it, and our own traits around the three APIs we depend on.
