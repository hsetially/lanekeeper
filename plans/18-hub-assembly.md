## Shape (what T1 to T8 build together)

Startup order in `process::run(settings, edges, shutdown)`. Differences from the survey are marked (*).
1. `main`: parse arguments and settings (exit 2, typed message, no values); install the aws-lc-rs default provider (*); create the SIGTERM and SIGINT streams before anything is spawned (*); telemetry.
2. `Edges` (*): the ports that reach outside the process (secrets, KMS signer and envelope, the Google ID token verifier, identity's HTTPS client, GitHub, the checkpoint bucket, clock). `Edges::google(&settings)` builds the real ones from `GoogleEndpoints::production()`; tests and the dev example fill the struct with fakes. No fake is compiled into the `hub` binary.
3. Concurrently, each with a timeout: database pool and schema probe (*); web certificate and key; both CA certificates and both `CaIssuer::new` probes (*).
4. `PgAuditLog`, `PgLeases` (this replica's `PeerName`), `PgEventBus` and `.start(closing)`, `PgBlobStore`, Git mirror, reader, announcer, fetch worker, syncer, webhook (with `PrLinks`).
5. Two server identities and their rotation tasks, `ConnectionRegistry`, `HubGateway`, `JoinService`, `AgentService` plus `SentinelService` on one `Routes`, `ReplicaService`.
6. Identity (`Sessions`, `RevocationListener`, `OidcLogin`, `PgUsers`, `UserAdmin`, token verifier), registry services, writes (`WriteHub`, vault, PR jobs, Teams notifier), MCP.
7. `JobRunner`: register 4 platform + 11 registry + 4 writes jobs, then `start()` (*: after everything that is registered); identity's three audit jobs spawn; plain tasks (PR-state watcher, auto-notifier, registry warm-up after readiness).
8. `Hub::build`, then module metrics registered on `hub.metrics` (*), four listeners bound, readiness.
9. Shutdown: not ready, drain period, stop accept loops, stop jobs, wait for listeners, flush telemetry, exit 0; a second signal exits at once.

Layer order of the web router, outermost first: request context, security headers, error normalisation, drain gate, limits (per-IP bucket, body cap), `AuthLayer`, `CsrfLayer`, then the routers with their guards. The per-IP bucket stays outside authentication, so a flood of random cookies cannot cause one database read each.

## Risks

**Security.**
1. **CSRF coverage depends on layer order.** `CsrfLayer` is a no-op without an `AuthContext`. Mitigation: `Deps.session` is required and cannot be omitted by a release build; `csrf_all_routes` walks every route of `Hub.routes` with a real session; a layer-order test fails if `AuthLayer` moves.
2. **A fake session store in production.** The placeholder `DenySessions` authenticates nobody; no fake is in the `hub` dependency graph (`release_build`, `hub-lint`). The dev example is an example target and is never built into the image.
3. **Unauthenticated work before the guard.** Authentication runs after the per-IP bucket; body buffering stays bounded by the global cap (G8). Residual, already open: up to 4 MiB of JSON is buffered per request before any guard (03b evidence), limited by the bucket and the 30 s timeout.
4. **Stream after logout (S2).** Closed by the Extra-path of G2, or accepted as a stated residual.
5. **`hub seed` registers identities.** Whoever can run it with the app credential can make a service account a swimlane's agent. Mitigations: validated file, `--dry-run`, never deletes, one audit event per changed row, the Job exists only where 09 deploys it. Residual: the Job's operator is not recorded in the event (the actor is the component); the file's SHA-256 is in the `diff`.
6. **Migrator credential.** Read from a file, never logged, refused for the wrong role, never mounted in the hub pod.
7. **Retention deletes by default.** Off unless enabled, dry-run first (G16).
8. **Secrets in start-up errors.** Every start error is a fixed message naming a variable or a component; a process-output scan with planted values is in T1 and T2 tests.
9. **Two TLS providers.** `install_default` first; the HTTPS Git leg is tested in the composed process (G21).

**Performance.**
1. **Startup (P11, 10 s).** Four KMS calls (two probes, two certificate signings), about seven Secret Manager reads and the pool connect are sequential in the obvious wiring; they run concurrently here, each wrapped in the hub's own start-up timeout (a setting, default 8 s) because the library's CA probe has a fixed 30 s (`ca/mod.rs:41`) that would by itself break the budget. The bench uses fakes at the edges, so it does not show real Google latency; the evidence says so, prints a phase breakdown, and an opt-in run against a real project (the existing `gcp_real` convention) records the real figure if a project is available. A first start on an empty mirror volume waits for the network and is outside the budget (as `startup.rs` already states).
2. **Memory (P11).** Blob cache 512 MiB, registry corpora up to 256 MiB, 50,000 sessions, a 400,000-entry tree index and the user cache are all bounded by settings; the RSS at ready and after a request burst is recorded. The platform's share was 746 MiB; the whole hub is proven by prompt 16.
3. **Per-request cost.** The adapter adds a cached user lookup and a second `AuthContext` read; measured against 2 ms (CC1).
4. **Database pool and job load.** 19 leased jobs poll their leases on every replica; the pool may run short (G27). The warm-up starts after readiness so it cannot delay it.
5. **Environment.** `cargo deny` and `cargo audit` on a new fuzz lockfile depend on the advisory state of `main` (D134 is on `main`; D135 and its zstd ignore are still on a branch). The new lockfile is generated against the workspace pins; if an advisory outside D134's override fails it, I stop and report.
