### The SSE security gap, and its fix (`c0f97a1`, S4, S12)

After the merge `DomainEvent::UserSessionsRevoked` (internal, names a user, no swimlane) went through `RoleVisibility`'s `_ => user.allows(Role::Viewer)` and `events/sse.rs` would have streamed it to every active Viewer, live and on replay. Tests first, run red (`events_sse`: 6 failed and `events_sse_cluster`: 2 failed, each for the right reason: the internal event arrived before the probe, or `kinds=user_sessions_revoked` was accepted), then the fix, then green:

- `events_sse.rs`: `an_internal_event_is_never_streamed_live_to_a_viewer_or_an_admin` (viewer, admin, a swimlane-filtered and a kind-filtered stream), `an_internal_event_is_never_replayed_to_a_viewer_or_an_admin` (Last-Event-ID replay), `an_internal_event_that_is_both_replayed_and_live_is_still_dropped`, `a_resync_and_the_other_kinds_still_reach_the_users_they_reached_before`, `the_default_visibility_rule_refuses_an_internal_event_to_every_role`, and two new bad queries in `sse_query_bounds_are_enforced`. (My first version of the both-paths test passed without the fix because the probe came before the leak in the log; I rewrote it so that it fails without the fix.)
- `events_sse_cluster.rs` (three replicas, real Postgres): `an_internal_event_crosses_the_replicas_on_the_bus_and_reaches_no_browser` (published through `publish_in_tx` and through `publish` on replica 1; an in-process subscriber on replica 2 still gets it, which 03a's session cache needs; no browser of either role on any replica does) and `an_internal_event_in_the_outbox_is_not_replayed_to_a_resuming_browser` (resume on another replica).
- `events_wire.rs`: the new variant round-trips through the outbox envelope, and the golden snapshot has its line. The `sse.rs` unit test `an_internal_kind_cannot_be_asked_for_and_agrees_with_the_event` is new too.
- The fix: one `deliverable` check on both the replay and the live path (internal events first, then `Resync`, then the visibility rule); `kinds=user_sessions_revoked` is a 400 (the OpenAPI `EventKind` list does not have it; it is refused whole and never dropped, because an emptied list means every kind); `is_internal_kind` has no wildcard arm; `RoleVisibility` refuses internal events to every role as well. `Resync` and every other kind behave as before (the existing tests pass unchanged). Nothing else in `hub-platform` or `hub` matches exhaustively on `DomainEvent` or `EventKind`: `EventKind::of` is in `ports` (done by 03a's contract PR), `events/wire.rs` is serde-based, `git/sync.rs` filters on `GitHeadMoved` and has a `Some(_)` arm, the fuzz targets do not touch events, and no corpus seed holds an event.
- `docs/threat-model.md` has a row for it (`e580406`), with those tests as proof.

### A flaky test of mine, found by the merged run (`05166af`)

The first `just verify-03b` on the merged tree failed in `platform-test`: `lease_race::the_local_guard_never_outlives_the_database_lease` (`local 29.997345327s must not exceed database 29.995099`). Root cause: the test read the guard's remaining time, then the row's remaining time with a second query, and allowed 1 ms for the difference; the difference is that query's latency minus the acquire's, so it fails when the box is busy. Reproduced with the code unchanged: 1 failure in 15 with eight busy loops competing (`local 29.997267 against database 29.990464`); 0 of 12 alone and 0 of 6 as part of the binary on a quiet box. The assertion now allows the query's own duration (the database's `now()` lies between the instants around the query) plus the 1 ms; the same invariant, no false failures. 0 failures in 40 runs under the same eight busy loops. The lease code is untouched. The test was written in round 1, so the flake predates the merge; the merge did not cause it.

## Assumptions

Known items for the PR text. A15, A16 and A19 refer to the plan's question ids.

1. **A15, sqlx and ring.** The hub binary enables `tls-rustls-ring-native-roots` for the database leg only, because every sqlx variant on aws-lc-rs failed `cargo deny` or pulled `webpki-roots`. Consequence: `ring 0.17.14` is compiled into the `hub` binary (`cargo tree -p hub -i ring`), so rustls has two providers compiled in there. The hub's own listeners, the CA and rcgen use aws-lc-rs. `hub-platform` alone has no ring. Not proved by a test: which provider the `gix`/reqwest leg picks when both are present (the HTTPS mirror test `git_mirror_http` passes, so it does work).
2. **A16, gix.** `gix` with `blocking-http-transport-reqwest-rust-tls` brings `reqwest 0.13.5` as a transitive dependency only; there is no direct `reqwest` use. Human decision recorded in `plans/03b-hub-platform.blockers.md`: `deny.toml` `[graph].targets` is narrowed to `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`. Side effect: the Windows, macOS, Android and wasm32 dependency graphs are no longer checked by `cargo deny` for any crate.
3. **A19, webhook body cap.** 1 MiB, the number in `api/openapi.yaml`, not the 4 MiB of the plan's proposed default. A push webhook over 1 MiB gets 413 and the 60 s poll picks the change up.
4. **`BlobPolicy::allowed` is `async`** (the real policy lives in 05's registry and has to read the database).
5. **Sentinel join is audited as `AuditAction::AgentJoined`** (no sentinel-specific action exists in `ports::audit::AuditAction`).
6. **Contract follow-up on `ports::conformance::event_bus`.** The suite assumes `publish` is visible to a subscriber synchronously; with the outbox relay (D80) delivery is asynchronous, so `crates/hub-platform/tests/outbox.rs` runs the suite through a `Settled` wrapper that waits for the relay. The suite should grow an async-settle hook in a `contract-change` PR.
