## Review round 2: what changed

- **Blocking (S9): a stored time could stop the verifier. Fixed.** The round 1 select list cast `extract(epoch FROM at) * 1000000` to `bigint`, which raises an error for `at = 'infinity'`, `'-infinity'` and `'294276-01-01'`. An owner who disabled the trigger could set one on an early row: the query failed, the run ended as `Errored` (no notification), and a tamper on any later row and every checkpoint went unexamined. Now `at` is selected through `CASE WHEN isfinite(at) THEN ...::numeric(40,0)::text END` and parsed as an `i64`; a time that is not finite or does not fit is `None`, never the copy of an event's time, so `Column::At` differs.
- **The rule, in general:** a value of a copied column that cannot be decoded (a `jsonb` holding a number or nesting `serde_json` refuses, a `NULL` where the schema forbids one) is reported as `ColumnsDiffer` naming that column, and the walk goes on. A `NULL` in `prev_hash`, `hash` or `event_json` is a hash failure at that position. Only a failure of the query itself (connection, timeout, a missing column) is `VerifyError::Database` and `Errored`; the line between the two is one function (`is_decode_failure`) with a unit test and an integration test (`a_database_error_is_still_an_error_and_not_a_finding`, renamed in round 4 to `a_query_the_database_refuses_for_the_shape_of_its_tables_is_a_finding_and_a_dead_connection_is_an_error`). **[Round 3: this was too broad. It held for the copied columns of `audit_events` only; a checkpoint column that could not be decoded was still an error, and an error discarded the findings made before it. Both are fixed in round 3 (above): a stored value in any column the verifier reads, in either table, is a finding; only a failure of the query is an error; and an error keeps the findings. Round 4: a missing or retyped column is no longer a plain `Database` error: it is `SchemaChanged`, an error and a finding that alerts the same night.]**
- **Tests, red first:** the reviewer's scenario through `nightly().run_once()` (infinity on seq 2, a changed event on seq 5, a checkpoint mismatch at 12: three failures, one alert), the `-infinity`, `294276-01-01` and `jsonb` variants, 23 hostile-value cases for all 16 columns in the case table (52 cases in all), and a coverage test that every column has one. 7 tests failed against the round 1 code. Six mutations were each caught; one (the decode-failure arm for the three chain columns) is not reachable on a UTF-8 database and has no test.

## Review round 3: what changed

The round 3 reviewer returned CHANGES REQUESTED on `a9451ed`: two blocking findings and five non-blocking ones. The human explicitly authorised this round past the protocol's three. All seven are fixed in one commit, `03a/FINAL: review round 3 fixes`, tests first (details, red phase and mutation checks in the evidence file).

- **Blocking 1 (S9): a `NULL` in any `audit_checkpoints` column ended every nightly run as `Errored`, silently and for good, and threw away the chain findings. Fixed.** The checkpoint reads kept the old rule (any decode error is `VerifyError::Database`) after round 2 had changed the `audit_events` reads. Now a checkpoint column that is `NULL`, undecodable or over its bound is `FailureKind::CheckpointColumnsInvalid`, naming the position and the column names only (S10); that checkpoint is skipped and the walk goes on. A checkpoint at a position that is not positive is `CheckpointHeadMissing`. `ChainVerifier::verify` now returns `Result<VerifyReport, VerifyAborted>`, and `VerifyAborted` carries the findings made before the error; the chain and checkpoint halves run whatever happens to the other; the nightly job alerts on those findings and reports the new `NightlyOutcome::Incomplete` (`Errored` only when there were none). Test: all four checkpoint columns, 16 cases (`NULL`, oversize, in-range but wrong), each with a tamper at 5: exactly the two failures, one alert, no error.
- **Blocking 2 (rule 5): the verifier read every column with no bound. Fixed.** Each column is now bounded in the select (`CASE WHEN octet_length(col) <= N THEN col END`, for `jsonb` on its text form) with a bitmask of the columns left out; an oversize value is never sent, buffered or decoded and is reported as that column differing. The bounds come from the one the log enforces: a copy is a part of an event, an event is at most 1 MiB (`MAX_EVENT_JSON_BYTES`), so text is bounded by 1 MiB, `jsonb` text by 2 MiB (it prints a space after `,` and `:`), a hash by 32 bytes, the checkpoint's columns by what the job writes. A test that sends the four batch queries against rows with up to 50 MB per column asserts no row comes back with 8 KiB; a memory test (own binary, `VmHWM`) shows the peak growing by 473 MiB before and about 1 MiB after for a row with 80 MB in two columns; the largest row the bounds allow (about 14 MB) costs 45 MB. Rows are streamed and compared in chunks of at most 1,024 rows or 16 MiB, so the memory is a chunk and not the 5,000-row batch (the worst legitimate row is about 72 KiB).
- **N1: rows at `seq <= 0` were never looked at. Fixed.** The first batch of each walk has no `WHERE`; a row below position 1 is `SeqNotPositive`, reported and skipped (the real chain is still checked from the genesis hash); a row with no `seq` is found by one probe per table (an index scan while the key exists). Tested with -5, 0 and `i64::MIN`, with a later tamper, and with `NULL` `seq` (set on a row, forged at the tail, and a whole batch of such rows: my first version looped on that, found by its own test).
- **N2: the text overstated the rule. Fixed** in the module docs, the threat model, the evidence and here (the round 2 text below carries a note).
- **N3: the comparison ran on the async runtime. Fixed:** per chunk in `spawn_blocking`; a single-threaded-runtime test keeps a 2 ms ticker alive while 25 MB are verified.
- **N4: the headline named the first failure. Fixed:** the most severe (chain, then checkpoint, then columns, then an unreadable bucket), whatever order they were found in.
- **N5: no timeouts. Fixed:** every query runs in a transaction with `SET LOCAL statement_timeout` (5 min) and `lock_timeout` (30 s), the client gives up 30 s later; a table locked by an owner ends the run as `Errored` in bounded time and the lease is no longer renewed. **Not added:** a notification on `Errored` (the recorded human decision, follow-up 17 below).
- **Tests:** `audit_verify` 34 to 61, lib 123 to 132, one new binary (`audit_verify_memory`, 2 tests): 436 to 474. 27 of the new integration tests, 9 unit tests, 2 memory tests. Red first against the old behaviour behind the new types (16 of 58 failed at the first run, the memory test, 2 unit tests); 23 scratch mutations (guards removed or weakened), all re-run against the final tree after the container restart and all caught (every run had at least one test fail; files restored and compared); three first attempts in the earlier session that were not caught were strengthened.

- **Blocking (S9): the round 3 bound for the two `jsonb` columns could itself fail the query. Fixed.** The select printed the column to measure it (`octet_length(col::text)`, twice a row), and a `jsonb` number is stored compactly and printed in full: 9,000 numbers of `1e131000` are 2.5 KB stored (144 KB decompressed) and print as more than a gigabyte, which the server refuses (SQLSTATE 54000, `out of memory`); 7,000 print as 917 MB and take 8 to 13 seconds each time. The INSERT-only app role can write such a value, so one row ended every nightly run as `Errored`, with nothing after it verified and nothing notified. (My earlier account of this limit, that it needed a value of hundreds of megabytes and an owner, was wrong and is removed everywhere.) Now each `jsonb` is vetted in one searched `CASE`, in this order, each check evaluated once and only if the ones before it did not apply: stored size over 8 KiB; decompressed size over 8 KiB (so at most about 2 MB is ever decompressed, and nesting is under 1,024 levels, far under where `jsonpath` itself fails); a number past the range of an `i64` or not an integer, found by value with `jsonpath` without printing it (`1e131000`, `-1e131000`, `1e-16383`); more than 16 numbers (an integer can still carry a scale that prints 16 KB); and only then `octet_length(col::text) > 16 KiB`. A value that is not vetted is sent as the JSON `null` literal, which no event holds in these columns, and is reported as that column differing. The limits come from the types (an actor or the evidence of an attribution is about 700 bytes at most; the limit is more than ten times that, and a test fails if the types grow to a tenth of it), not from the 1 MiB event, which also keeps a poisoned row to milliseconds. Every other cast and render in the verifier's SQL was audited: `octet_length` on `text` and `bytea` reads the length from the header and cannot fail; `at` is cast only when finite; there is no other cast, and a test that parses every `::` in every query keeps it so. Tests through the INSERT-only pool: a poisoned row, three legitimate events after it and a tamper further on, for the 9,000- and 7,000-number values, `-1e131000`, `1e-16383`, `0e-16383` (zero with the largest scale), a number past an `i64`, nesting 16,000 deep (where `jsonpath` fails) and 1,100 deep, in both columns: `Failed`, never `Errored`, under 5 s, the poisoned column named and the later tamper found; ten poisoned rows together: `Failed` in under 10 s (round 3's code spent 125 s on them in the red run).
- **N1: a position used twice could finish `Clean`. Fixed.** The walk now carries the last position across chunks and batches; a batch starts at the last position read (`seq >= $1`) and skips the rows of it that the batch before compared, so all rows that share a position are in one batch; a repeated position is `EventPositionDuplicated` (checkpoints: `CheckpointPositionDuplicated`), once per position. A position held by more rows than a batch is reported and compared only as far as a batch reaches (stated). The checkpoint's event is now looked up and not joined (found by a test: two events at a checkpoint's position made the checkpoint appear twice). The edge is tested for five repeats against batches of 0 to 5,000 rows, and for checkpoints across a 500-row edge.
- **N2: dropping or retyping a column blinded the verifier and said nothing. Fixed.** SQLSTATE class 42 and a column that comes back as another type are `VerifyError::SchemaChanged` and a finding (`FailureKind::SchemaChanged`, SQLSTATE only), so the run alerts that night (`Incomplete`) and raises `audit_verify_schema_changes_total`; timeouts, connections, resources and the rest stay errors. Every column of both tables was retyped to `int` and dropped in a test; each gave an alert that night (`approval_id` made `int` keeps the query working and is a column difference); a value-preserving retype (`text` to `varchar`) is `Clean`, stated.
- **N3, N4: docs.** The statement timeout runs while the client compares a chunk (stated in the module docs and the threat model; a batch of hostile rows near the size limit was not measured against it); the module docs, the threat model, the evidence and this text are corrected, the wrong account of the `jsonb` limit and the wording "loud, not silent in the old way" are gone.
- **N5 (the human's option 1): an alert after N unfinished nights. Done, with a limit.** `Errored` and `Incomplete` nights are counted; from the second in a row (`DEFAULT_ALERT_AFTER_FAILED_RUNS`, `with_alert_after`) the notifier is told "Audit log verification could not complete N nights in a row (last error: ...)" with the class of the error and nothing else, every night until a run completes; `Clean` and `Failed` reset; `NotLeader` and `LeaseLost` neither count nor reset (decided, tested). New gauge `audit_verify_unfinished_runs_in_a_row` and counter `audit_verify_schema_changes_total`; the Prometheus expressions are in `metrics.rs`. **The count is held in memory** (the `Leases` port has no payload and `db/migrations/` is a contract path), so a pod restart or the lease moving resets it: a pod that restarts daily and fails nightly never reaches two. Until a human approves a contract-change PR adding a small `audit_verify_state` table (`id boolean PRIMARY KEY CHECK (id)`, `unfinished_runs integer`, `last_error text`, `updated_at timestamptz`; `SELECT, INSERT, UPDATE` for `lanekeeper_app`; one row written after each run), operations should alert from Prometheus on `increase(audit_verify_errors_total[3d]) >= 2` and `increase(audit_verify_runs_total[36h]) == 0 or absent(audit_verify_runs_total)`.
- **Tests:** 511 passed, 0 failed, in 24 binaries (474 before), with default threads and with `--test-threads=1` (lib 141 from 132, `audit_verify` 89 from 61), no `SKIPPED` line; `cargo test -p xtask` 95 passed. ## Gate failure found on a second platform

The human ran `just verify-03a` on a Rocky Linux 8.10 VM (4 vCPU, 15 GiB, xfs, Docker 29.9.0 on overlayfs, cgroup v1, SELinux off, gcc 8.5, cmake 3.26.5, rustc 1.88.0 and `nightly-2026-09-14`) at `b6d3e23` on 2026-10-12. The build of `aws-lc-sys` 0.45.0, `ring` and every `-sys` crate with GCC 8.5 worked and `identity-lint` passed. `cargo test -p hub-identity` gave 506 passed, **5 failed** of 511; the five are in `audit_verify` and every other binary was exact.

- **Cause.** All five fail with SQLSTATE 54001 `stack depth limit exceeded` raised by the *test's own setup INSERT*, before the verifier runs. The tests built `jsonb` values nested 16,000 deep. What a server can parse is `max_stack_depth` over the stack one level uses, which depends on how the binary was compiled: Ubuntu's 16.15 takes 16,300 levels at 2 MB, so 16,000 worked in the sandbox and in two reviewers' sandboxes; the Debian-built Postgres of the pinned image takes fewer. **Reproduced** without Docker by starting the same Ubuntu server with `max_stack_depth` 1536kB and 1MB: the same five tests fail, the same SQLSTATE, at the same two sites (`audit_verify.rs:2363` and `:2682`); they pass at 2MB and 6MB.
- **Fix, tests only.** The tests no longer name a large depth: each probes the server (bisection on 54001, once per test, on the test's own database) for the deepest nesting it takes as input and the deepest the production `jsonpath` check reads, and builds from that. Where the size gate is the point they use its own numbers (1,024 levels are 8,192 bytes decompressed): 1,000 and 1,024 are under it, 1,025 and 1,100 over. The 'where `jsonpath` would fail' row is now the probed depth. A new test runs the verifier at a ladder of depths up to the deepest the server takes and asserts the invariant that matters: never `Errored`, the poisoned column named and the later tamper found, at every depth the server accepts. A server too small for the tests fails them under `LK_REQUIRE_DOCKER=1`, with a message naming the probed limits, and prints `SKIPPED` otherwise. No test sets or raises `max_stack_depth`. Three tests added (514 in all, from 511); one renamed (`jsonb_nested_past_what_jsonpath_reads_is_a_finding_not_an_error` to `jsonb_nested_as_deep_as_the_server_takes_is_a_finding_not_an_error`); mutation checks in the evidence.
- **Production margin, measured with the real nightly job.** The select's size gate keeps every value that reaches `jsonpath` to 1,024 levels or fewer, and a value nested past what the server parses cannot be stored at all. The verifier returns the right finding (not an error) for the largest value the gate lets through (1,024 deep) at `max_stack_depth` down to **200 kB** and ends `Errored` at 192 kB, about a tenth of the 2 MB default; values over the gate are safe at every setting down to PostgreSQL's minimum of 100 kB. No production code changed. **Known gap 16 below is the real limit and needs a human decision.**
- **The `Atomic::fetch_update` deprecation** on the pinned nightly (`verify.rs:1556`, renamed `try_update`, which stable 1.88 lacks) is replaced by a `compare_exchange_weak` loop with the same saturating increment: warning-free on both, covered by the tests of the nights in a row.
- **Benchmarks on that VM** (xfs under overlayfs, about 23% CPU steal, load 1.4 to 3.3 on 4 CPUs): `identity-bench` run 1: `P7` 0.011, `P7.cold` 1.386, `P12` 3.100 ms; run 2: 0.007, 0.991, 5.794; run 3: 0.006, **2.287 (FAIL, budget 2)**, 3.554; full `just bench` and `bench-check`: 0.006, 0.568, 3.023. **P12 exceeded its 3 ms budget in all four runs and P7.cold once. This is measured data, not a pass, and an open human decision** (Known gap 15).
- Also on the contract PR branch `01de877`: `db_migrations` 32/32 with pgvector proven, `just verify-01` and `just db-verify` green, `cargo test -p xtask` 102 passed, and a full `just verify` green.
