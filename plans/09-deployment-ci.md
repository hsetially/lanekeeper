Summary for the human. Four things need a decision before coding starts. The details are in "Extra paths" and "Ambiguities" below.

1. **Acceptance 3 is blocked by work this prompt does not own (A1).** `crates/hub/src/main.rs` exits 1 by design until 03a and 05 are composed into the binary. The 03a and 03b PRs say "prompt 09 composes the binary", but prompt 09 says "Out of scope: application code" and owns nothing under `crates/hub/src`. So `/readyz` cannot pass on any replica. I propose leaving composition out of 09 and having a human assign it. The kind test gets built and runs, and acceptance 3 stays unticked until composition lands.
2. **Extra-paths for the Dockerfiles and the hub hardening test (A2, A3).** The prompt's "Dockerfiles" cell is not backticked, so the guard does not count them as owned. Also, `crates/hub/tests/hardening.rs` (owned by 03b) allows only two things in the final image. Adding the embedding model makes three.
3. **How GCP resources are declared (A4).** These are the buckets, KMS keys, IAM bindings, Cloud Armor, the Binary Authorization policy and the GitHub Workload Identity Federation pool. I propose Config Connector manifests, so that one toolchain (helm, kubeconform, conftest) covers everything. Terraform is the alternative.
4. **Binary Authorization and keyless cosign (A5).** To my knowledge, Binary Authorization verifies key-based signatures, not Fulcio identities. I propose a second cosign signature with a Cloud KMS key that only the CI identity can use. Binary Authorization checks that signature; the keyless signature and the provenance stay for CI and humans.

## Risks

- **Security: the trust root of signing and admission.** If the KMS cosign key or the GitHub WIF binding is too broad, any workflow or branch could sign images. Containment:
  - the WIF attribute condition pins the repository, and `ref` to `main` or tags;
  - only the `publish` job has `id-token: write`;
  - zizmor and actionlint gate the workflows;
  - pull requests from forks never get OIDC.
- **Security: CNPG secrets and the CA key.** CNPG's secrets include the CA private key, and the chart could expose it to the hub. Containment: `items: [ca.crt]` only, enforced by a policy test; the hub has no service-account token, so it cannot read the rest.
- **Security: network policy is name-based or unenforced.** FQDN policy only works where the cluster supports it, and a CNI without enforcement ignores every policy. Containment: the policies are tested as rendered, and the threat model states the residual risk for each cluster.
- **Security: ArgoCD drift on Secrets, and irreversible bucket locks.** Both are kept out of default values and need an explicit human value.
- **Performance (P11):** the hub's memory request is tied to `perf/budgets.toml` by a policy, so it cannot drift from the budget. The embedding model, about 130 MB as fp32, adds image size and start-up load time against the 10 s budget. The kind run measures time to Ready once A1 is resolved.
- **Performance of CI itself:** 3 replicas and CNPG in kind, plus fuzz and bench matrices. Every job has `timeout-minutes`, and benches run on a fixed runner, so noise doesn't make the gate flaky.
- **Delivery:** acceptance 3 depends on A1, and the exposure score in T8 depends on A15. Both are escalated up front rather than worked around.
